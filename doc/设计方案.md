# SQLBULL 定向 SQL 测试样例生成与反馈演化设计方案（第六版：实现边界与版本兼容定稿）

## 1. 背景与目标

SQLBULL 当前已经具备一套可工作的 SQL fuzzing 主链路：

    RSG 生成 SQL IR
    -> instantiator 补全标识符、类型和上下文
    -> DBMSConnector 执行
    -> ResultHandler 判断结果
    -> AFL coverage / RSG reward
    -> QuerySequence / FuzzingSequenceQueue 保存和变异

本次改造不以重写 SQLBULL 为目标，而是在现有 RSG、IR、instantiator、DBMS connector 和 AFL 基础上，增加一套面向 SQL 测试样例生成的约束、观测和演化机制。

最终系统需要同时满足以下目标：

1. 合法性不下降。

   对普通查询，生成结果应尽可能通过语法解析、名称绑定、类型检查并成功执行。对生命周期类测试，允许出现预期的、可控的 SQL 错误，但 DBMS 必须保持存活，且错误应符合锚点定义的预期结果。

2. 有效复杂度持续提高。

   复杂度来自 JOIN、子查询、CTE、聚合、窗口、函数、类型组合、事务和对象生命周期关系，而不是单纯增加 SQL 长度。

3. 多样性持续保持。

   系统不仅要找到高 reward SQL，还要避免收敛到少量重复模板。结构、特征组合、事件序列和执行计划等维度均应保留多样性。

4. 支持用户指定锚点。

   用户可以指定结构要求、事件序列、对象关系、示例 SQL 或目标 DBMS 子系统。后续生成应在满足合法性约束的前提下，逐代提高与锚点的相关性。

5. 完整序列可重放。

   生命周期、事务、prepared statement、cursor、缓存失效等问题依赖同一 session 中的完整 SQL 序列，因此保存、评分和复现的基本单位不能只是一条 SQL。

6. 面向大样本和多轮运行提高命中概率。

   系统不承诺短时间内直接构造出最终高质量 seed，而是在高速、海量生成中逐步提高到达锚点阶段和偶发 terminal outcome 的概率。进程因内存、DBMS 故障或运维原因重启后，可以有条件地继承长期有价值经验；同时必须保留足够随机探索，使未被人工规则和历史统计覆盖的路径仍有持续出现机会。

当前最终交付只以 PostgreSQL 为实现目标；通用层保留 dialect/capability 接口，但 MySQL、MariaDB、SQLite、DuckDB、CockroachDB 的 guided 接入不属于本方案完成条件。

### 1.1 最终实现目标

本方案的最终交付不是一个无限扩展的“智能 SQL 平台”，而是 SQLBULL 中一条可独立关闭、可回放、资源有界的 PostgreSQL 定向生成闭环。完成态必须同时具备：

1. **稳定执行底座**：每个 QueryStmt 按单 command 执行，正确处理 SQLSTATE、timeout/cancel、result drain、事务状态、session reset 和完整序列 replay；
2. **三路生成**：保留原始 RSG 随机路径，增加受约束 RSG/targeted mutation，以及少量 PostgreSQL 生命周期 typed builder；
3. **明确锚点**：AnchorSpec 能表达结构、事件、对象关系和 terminal goal，并由 PostgreSQL 17 capability/semantic oracle 编译；
4. **合法且多样的有界归档**：Completed、Frontier、Exploration、Fault、Quarantine 职责分离，内存、磁盘、cell、beam 和 reservoir 均有硬上限；
5. **两时间尺度反馈**：轮内只用有限 StrategyProfile 做快速调整；跨轮优先恢复可重放代表 seed，统计 warm start 为可选增强；
6. **受保护的随机性**：legacy、uniform profile 和 exploration reservoir 始终保留不可被经验覆盖的选择下限；
7. **版本化产物**：任意长期保存结果至少能在后续工具版本中被识别并作为完整 SQL 序列重放；不能安全迁移的 IR、feature、score 或 policy 自动降级为重算或 replay-only，而不是错误复用。

最终验收以结果合同为准：在相同 PostgreSQL build、scenario、预算和随机探索下限下，GUIDED 的滚动合法率不得低于配置保护线；多样性不得坍缩；目标 stage/terminal hit 的单位有效样例命中概率或到达成本相对 baseline 有统计改善；异常、重启和旧版本产物不得阻塞 LEGACY 随机生成。只提高平均 reward 或生成更长 SQL，不算完成。

完成边界如下：

| 级别 | 内容 |
|---|---|
| 必须完成 | 阶段 0～5、6A；ReplayBundle/SeedArtifact/ArchiveManifest；archive-only 跨轮恢复；阶段 7 的安全 plan/coverage observation 子集 |
| 条件启用 | 阶段 6B 的统计 prior；只有相对 archive-only 有独立收益才成为默认能力 |
| 明确延期 | contextual/grammar learner、protocol-level prepared action、通用 SQL->IR importer、其他 DBMS guided builder |

因此“跨轮经验”至少由代表 seed 重放和重新评价实现，不要求统计 prior 才算完成；无法证明收益的 6B 可以永久保持关闭。

## 2. 非目标

第六版确定不纳入当前最终交付的内容：

- 使用深度强化学习、通用 contextual bandit 或 grammar-rule learner；
- 动态同步完整 pg_catalog；
- 精确证明某条 SQL 一定进入指定源码函数；
- 一开始就支持任意 SQL 文本锚点到完整 AST 的解析；
- 实现其他 DBMS 的 guided/directed builder；
- 用 query plan 替代 coverage 或执行结果；
- 持久化每条普通 SQL 或完整在线历史；
- 从有限失败样本自动学习永久 blacklist/hard rule；
- 为追求短期 anchor 分数把随机探索概率降为 0；
- 任意 PostgreSQL major 之间直接复用 plan/coverage/score/policy；
- 将当前 C++ IR 内存布局作为长期稳定的跨版本文件格式。

本方案运行在本地或云服务器 Docker 沙盒中的测试 DBMS 上。崩溃、assert、sanitizer 和异常行为均只用于 DBMS 健壮性测试。

### 3.2 必须先修复的代码问题

1. source of truth 不明确。

   Dockerfile 直接复制 `PostgreSQL/docker/rsg_cpp`，但 `PostgreSQL/scripts/setup_postgresql.sh` 会先删除该目录，再从 `Common_Tootls/rsg_cpp` 复制。当前开源目录中不存在后者。必须先确定唯一公共源码位置，否则修改可能被构建脚本覆盖。

2. `TYPESTRING` 路径不安全。

   `QueryStmt` 支持字符串类型，但 PostgreSQL 主循环在判空前直接访问 `cur_stmt->stmt_ir`，RSG reward 和 instantiator 也普遍假设 IR 存在。directed builder 接入前必须提供安全访问接口，并禁止外部直接解引用可空 IR。

3. PostgreSQL connector 使用简单分号切分。

   当前 `run_target()` 使用 `string_splitter(cmd_str, ";")`。这会破坏 dollar-quoted 函数体、`DO $$...$$`、字符串和 quoted identifier 中的分号。每个 `QueryStmt` 应作为一个协议执行单元原样发送，并优先使用只允许单个 command 的 extended query 接口 `PQsendQueryParams(..., nParams=0)`。不能用客户端分号扫描承担 PostgreSQL lexer/parser 的职责，也不能改用允许多 command 的 `PQsendQuery` 后假设只有一条结果。

4. 执行结果缺少结构化信息。

   当前主要依赖结果字符串中的 `ERROR`、`unexpectedly` 等关键字，无法可靠区分语法错误、名称错误、类型错误、事务中止、预期生命周期错误和 DBMS 内部错误。PostgreSQL 应读取 `PG_DIAG_SQLSTATE`、severity 和 transaction status。

5. `FuzzingSequenceQueue` 不能直接作为学习队列。

   当前分数更新存在 hit count 为 0 时参与除法的问题；分数只映射到 group；追加变异结果时默认清空整个 group；`previous_sequence` 使用裸指针。该结构无法安全承载多样性归档和可重放 lineage。

6. query plan 反馈链尚未形成。

   PostgreSQL query plan handler 是空实现，现有接口也只接收 SQL 和已有结果，没有负责发起 EXPLAIN 的 observer。`has_new_query_plan()` 的新颖性判断逻辑也需要修正。

7. 当前生成 API 无法保证 QueryFamily。

   `RSG::generate_stmt_with_stmt_type()` 只能指定根语句类型和递归深度。选择 `IRTypeSelectStmt` 并不保证出现 JOIN、WINDOW、CTE 或相关子查询。因此“LearningController 选择 QueryFamily 后仍直接调用原 RSG”并不足以完成定向生成。

8. 当前合法性能力仍有限。

   PostgreSQL instantiator 已能维护部分表、列、索引、alias 和 DataAffinity 信息，但函数实例化被禁用，复杂聚合、窗口、嵌套作用域、事务性 DDL 和对象依赖仍缺少统一模型。

9. 存在未纳入配置的硬限制。

   主循环当前固定最多生成 40 条语句、单条 SQL 小于 2048 字节；instantiator 拒绝超过 10 个子语句的查询。这些限制必须进入运行时配置和 ComplexityBudget，而不是分散在代码中。

10. 当前 database reset 不是合法的 PostgreSQL 恢复流程。

    现有 `reset_database()` 包含 PostgreSQL 不支持的 `CREATE DATABASE IF NOT EXISTS`，并尝试在当前连接上处理当前数据库。首期不在每个 seed 之间 DROP/CREATE database；改为固定测试数据库中的独立 schema，加上事务恢复、`DISCARD ALL`、schema 重建和 fingerprint 校验。database 级重建只能由连接到其他维护数据库的 supervisor 执行，且 `CREATE DATABASE` 不得位于事务块内。

11. 当前 libpq result loop 不符合 row-mode 调用时序。

    代码在 send 后正确调用了一次 `PQsetSingleRowMode()`，但在收到 `PGRES_TUPLES_OK` 后又调用一次；官方接口要求它只能在成功 send 后、任何 consume/get-result 前调用。timeout 分支也会提前退出 result loop，再主动断开连接。重构时不能局部修补 switch case，而应把 send、row-mode、poll/cancel、drain-to-null、transaction status 和 connection disposal 实现为单一可测试状态机。

### 3.3 PostgreSQL 17 规范基线

仓库包含 `PostgreSQL/docker/postgres-REL_17_4`，因此首期以 **PostgreSQL 17 major semantics** 为功能基线，而不是跟随官网 current 版本。运行时仍必须记录实际 `server_version_num`、`PQserverVersion()`、libpq version、PostgreSQL build id、grammar hash 和 scenario version；跨 major version 的 SQLSTATE 策略、plan hash、关键字集和 capability 不直接复用。

本版方案的 PostgreSQL 专项约束以以下官方 PostgreSQL 17 文档为准：

- [SQL lexical structure](https://www.postgresql.org/docs/17/sql-syntax-lexical.html)：token、分号、dollar quoting 和 identifier 规则；
- [libpq asynchronous command processing](https://www.postgresql.org/docs/17/libpq-async.html)、[single-row/chunked mode](https://www.postgresql.org/docs/17/libpq-single-row-mode.html)、[command result/error fields](https://www.postgresql.org/docs/17/libpq-exec.html)：单 command 协议边界、结果 drain、结果状态和错误字段；
- [libpq connection/transaction status](https://www.postgresql.org/docs/17/libpq-status.html)、[PostgreSQL error codes](https://www.postgresql.org/docs/17/errcodes-appendix.html)：session 健康、事务状态和 SQLSTATE 分类；
- [PREPARE](https://www.postgresql.org/docs/17/sql-prepare.html)、[`pg_prepared_statements`](https://www.postgresql.org/docs/17/view-pg-prepared-statements.html)、[DECLARE](https://www.postgresql.org/docs/17/sql-declare.html)：prepared statement 与 cursor 的 session/transaction 生命周期；
- [EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html)、[SELECT](https://www.postgresql.org/docs/17/sql-select.html)、[table expressions](https://www.postgresql.org/docs/17/queries-table-expressions.html)：plan 观测、SELECT scope、聚合/window/LATERAL 规则；
- [client connection defaults / search_path](https://www.postgresql.org/docs/17/runtime-config-client.html)、[SQL conformance](https://www.postgresql.org/docs/17/features-sql-standard.html)：对象解析、session 默认值和 SQL 标准/扩展边界；
- [DISCARD](https://www.postgresql.org/docs/17/sql-discard.html)、[CREATE TABLE](https://www.postgresql.org/docs/17/sql-createtable.html)、[CREATE DATABASE](https://www.postgresql.org/docs/17/sql-createdatabase.html)、[VACUUM](https://www.postgresql.org/docs/17/sql-vacuum.html)：session reset、temporary object 和事务边界。

这里的“标准”分两层：SQL 标准决定可移植语义，PostgreSQL 17 官方文档决定本项目实际 oracle。PostgreSQL 扩展（例如 SQL-level `PREPARE`、`DISTINCT ON`、`RETURNING`、dollar quoting）不能因为不是 ISO SQL 就被判为非法；反之，SQL 标准允许但 PostgreSQL 17 未实现的形式不能进入 PostgreSQL guided lane。

## 4. 设计原则

1. 合法性是约束，不是普通奖励。

   不能允许 coverage 或复杂度奖励抵消大量非法 SQL。候选样例先经过准入判断，再参与多目标评分。

2. 锚点必须可计算、可验证。

   “与锚点相关”必须落到结构谓词、事件自动机、对象关系、规范化特征距离或运行时证据，不能只依赖人工描述。

3. 奖励演化增量，而不是重复命中。

   主要奖励 child 相对 parent 的锚点进度、复杂度提升和新颖性，避免重复生成同一高分模板。

4. 保留多目标，不盲目压成一个总分。

   合法性、锚点距离、复杂度、多样性、coverage 和执行成本的性质不同。归档和 seed 选择使用 score vector；learner 排序时才使用归一化后的临时标量。

5. 区分意图、表面推断、文档语义和实际观测证据。

   SQL 表面包含 JOIN 只能说明可能进入 join optimizer/executor。满足 PostgreSQL 文档前置/后置条件可形成 semantic oracle，但只有 plan、coverage 映射或内部 instrumentation 等运行时信号才能提升为 observed subsystem evidence。

6. 生成、观测、评价和学习解耦。

   生成器不直接计算 reward，FeatureExtractor 不修改策略，LearningController 不直接操作 connector。

7. 尽量添加，不重写主体。

   保留 RSG/IR、instantiator、AFL 和现有 connector。新建 ValidityKernel、AnchorEvaluator、EvolutionArchive 等模块，通过兼容层逐步替换旧行为。

8. 所有结果必须可重放。

   保存 scenario、session 设置、完整 SQL 顺序、预期结果、随机种子、父 seed、DBMS build 和配置版本。

9. 基础设施故障不能变成学习信号。

   DBMS 尚未启动、reset 失败、磁盘写满、plan observer 报错等不代表生成策略错误。所有失败必须先归因到 query、infrastructure、observer 或 model divergence，再决定是否更新 learner。

10. 所有高风险路径必须有界并可降级。

    generation retry、repair、server restart、replay confirmation、archive 内存和磁盘使用都必须有明确上限。达到上限后终止当前 seed、隔离结果或回退到 observe/legacy 模式，不能无限重试。

11. 硬规则最小化，启发式规则不得冒充 PostgreSQL 语义。

    只有 PostgreSQL 明确语法/协议约束、绝对安全预算、已确认 capability，以及用户显式声明的 anchor invariant/forbid 可以成为 hard constraint。人工总结的“通常更合法”“大概率无效”“可能不相关”等规则只能作为 preference、repair hint 或低置信度观察，不能禁止随机路径生成候选。

12. 随机探索是受保护能力，不是 learner 剩余预算。

    LEGACY RSG、均匀 profile 探索和 novelty/reservoir parent sampling 都有独立、不可被历史 reward 降到 0 的配置下限。学习策略只能分配剩余概率，不能永久关闭一个仍满足 capability/safety 的 generator family。

13. 经验只提供有界先验，不能成为永久规则。

    跨轮只继承经过兼容性校验、衰减和伪样本上限约束的聚合统计，以及少量可重放代表 seed。当前轮的新证据必须能在有限样本内推翻旧经验；不持久化“永久禁用 profile”或由偶然失败自动产生的新 hard rule。

14. 学习开销不能跟生成量线性放大到热路径瓶颈。

    每个结果可以做常数级计数，但 policy 重算、archive 压缩、持久化和跨 core 合并按 epoch/批次异步进行。观测队列、checkpoint 和写盘都有容量与时间预算，达到上限时丢弃低价值经验或暂停学习，不能拖慢主生成链或引发新的内存问题。

15. 每个概念只有一个规范定义位置。

    §6 定义语义模型，§8 定义生成选择，§10 定义准入与奖励，§11 定义学习算法，§12 定义运行时 archive，§13 定义持久化和版本兼容，§19 只描述故障响应，§20 只描述上线门槛。实施计划和测试章节只能引用这些合同，不得再次定义不同的数据字段、兼容条件或降级语义；出现冲突时以前述规范章节为准。

## 5. 总体架构

```text
Persistent（可选）
  CampaignCheckpoint --EXACT_RESUME--> CampaignState
  ArchiveManifest + ReplayBundle --format/semantic gate + replay--> EvolutionArchive

Runtime
  AnchorDocument -> AnchorCompiler + DialectCapabilities -> GenerationPlan
  CampaignState + RunState -> LearningController -> ExplorationGuard
  ExplorationGuard -> 选择 source/StrategyProfile
    -> 原始 RSG | 受约束 RSG/targeted mutation | Typed Builder
    -> ValidityKernel(Catalog/Scope/Session)
    -> QueryStmt + DecisionTrace
    -> DBMSConnector -> ExecutionResult
    -> ObservationPipeline(Feature/Event/Object/Plan/Coverage)
    -> SafetyValidityGate + AnchorAdmissionGate
    -> ScoreVector / RewardProjection
       -> EvolutionArchive -> 下一代 parent/mutation/replay
       -> EpochReducer -> RunState
                       -> campaign delta/checkpoint（可选）
```

其中 `LearningController` 只产生建议分布，`ExplorationGuard` 负责应用不可被学习覆盖的随机下限、单 profile 概率上限和 capability/safety mask。`CampaignState` 是从跨轮 checkpoint 加载的只读慢变量；`RunState` 只保存当前轮 learner 的窗口、epoch 计数和选择表。Catalog/Session 由执行上下文拥有，HotSeed/SeedRuntime 由 EvolutionArchive 独占；这些进程内对象都不直接跨轮恢复。

### 5.1 运行模式

运行模式按能力递增，任何高级模式都可以降级：

    LEGACY
      仅使用当前 RSG、AFL 和原队列

    OBSERVE
      保持 legacy 生成，只增加结构化观测

    GUIDED_SHADOW
      计算 anchor、score 和策略选择，但不实际影响生成

    GUIDED
      使用受约束生成、archive 和 learner

    SAFE_FALLBACK
      发现系统性异常后停止学习更新，使用已验证的 legacy/random mixture

配置、构建或观测模块失败时，优先降级而不是让整个 fuzzing 进程退出。Campaign/checkpoint 持久化不可用时先关闭跨轮经验，不能因此停止随机 fuzzing；只有 source/build 不一致、DBMS 无法恢复，或连 queue/crash/reproducer 等必需输出也无法可靠保存时才停止运行。

### 5.2 Supervisor 状态机

全局 supervisor：

    INITIALIZING
      -> HEALTHY
      -> DEGRADED
      -> RECOVERING
      -> HEALTHY

    RECOVERING 超过上限
      -> SAFE_FALLBACK
      -> STOPPING

单个 seed：

    SCENARIO_SETUP
      -> PREFIX_REPLAY
      -> GENERATE
      -> PRECHECK
      -> EXECUTE
      -> OBSERVE
      -> ADMIT / FRONTIER / QUARANTINE

任意阶段失败先生成 `FailureClassification`，再决定：

- query failure：可以影响合法率和对应 strategy profile；
- infrastructure failure：不更新 learner，尝试恢复；
- observer failure：保留执行结果，丢弃对应辅助信号；
- model divergence：终止当前 sequence，reset 后验证 reproducer；
- confirmed DBMS fault：保存到独立 FaultArchive。

```cpp
enum class FailureDomain {
    NONE,
    QUERY,
    INFRASTRUCTURE,
    OBSERVER,
    MODEL_DIVERGENCE,
    CONFIRMED_DBMS_FAULT
};
```

## 6. 核心数据抽象

### 6.1 ValidityStage

合法性不是一个 bool，而是分阶段观测：

    GENERATED
    INSTANTIATED
    PARSE_ACCEPTED
    ANALYZE_ACCEPTED
    EXECUTED
    EXPECTED_OUTCOME_REACHED

PostgreSQL 不一定能直接分离 parser 和 analyzer 的内部状态，第一阶段可以结合 SQLSTATE 近似分类：

- `42601` 等：语法阶段失败；
- 未定义表/列、类型不匹配、函数解析失败：分析或绑定阶段失败；
- statement timeout、事务中止、约束错误：运行或状态阶段失败；
- 正常结果：执行成功；
- 锚点允许的 SQLSTATE：预期结果到达。

### 6.2 ValidityPolicy

不同锚点可以有不同结果要求：

```cpp
struct ExpectedOutcomeRule {
    AnchorStage stage;
    SqlEvent event;
    TransactionPhase transaction_phase;
    int server_major;

    bool success_allowed = true;
    std::set<std::string> allowed_exact_sqlstates;
    std::vector<Postcondition> postconditions;
};

struct ValidityPolicy {
    bool require_parse_success = true;
    bool require_analyze_success = true;
    bool require_execute_success = true;

    std::vector<ExpectedOutcomeRule> stage_outcomes;
    bool require_connection_alive = true;
    bool require_transaction_usable = false;
};
```

普通 SELECT 锚点默认要求成功执行。生命周期锚点可以在精确 stage/event/transaction phase 下允许特定 SQLSTATE，但不能把任意错误当作有效。postcondition 用于检查“prepared statement 仍存在”“cursor 已关闭”“transaction 回到 IDLE”等状态，防止只匹配错误码却未达到目标语义。

`stage_outcomes` 只覆盖命中的终局 stage，未命中时仍使用三个 `require_*_success` 默认值。同一 observation 最多允许一条 rule 命中；存在重叠、空 SQLSTATE、未知 server major 或互相冲突的 postcondition 时，AnchorCompiler 直接标记 UNSAT，而不是依赖配置顺序决定 oracle。

系统还要维护群体合法率保护：

    rolling_valid_rate(family, budget)
      >= baseline_valid_rate(family) - allowed_delta

如果某个 profile 持续低于下限，LearningController 应降低其 policy remainder 权重或回退到安全生成通道。

baseline 必须按 dialect、scenario、QueryFamily 和 budget 分层，并在固定 warm-up 样本数后才能启用保护线。样本不足时不根据短期合法率淘汰 profile，只允许探索或使用保守先验。DBMS build、grammar hash、scenario version 变化后旧 baseline 自动失效。

### 6.3 AnchorSpec

锚点是用户目标的统一表示。

```cpp
struct AnchorSpec {
    std::string id;
    uint32_t revision;
    std::string dialect;

    std::vector<AnchorPredicate> invariants;
    std::vector<AnchorPredicate> terminal_goals;
    std::vector<WeightedPredicate> preferences;
    std::vector<AnchorPredicate> forbid;

    std::vector<EventPattern> sequence_patterns;
    std::vector<SubsystemTag> target_subsystems;

    ComplexityRange complexity;
    ValidityPolicy validity_policy;
    CapabilityRequirements capabilities;
    RelaxationPolicy relaxation;
};
```

这里的 C++ 结构是编译后的运行时模型。用户文件使用版本化 `AnchorDocumentV1`，predicate/event/subsystem/type 都写稳定文本 id。新 reader 遇到未知 invariant、terminal goal 或 forbid 时必须返回 UNSUPPORTED，不能静默忽略后继续 guided；未知 preference 可以带诊断跳过。编译结果保存 `anchor_hard_semantics_hash`，由规范化后的 hard predicate、状态机、ValidityPolicy 和 capability requirements 计算，不依赖字段顺序或 C++ 容器布局。

这里必须区分：

- `invariants`：当前锚点的 guided prefix 在相应 automaton stage 必须满足，例如对象关系一致、已进入 WINDOW stage 后仍保留 window 特征；它不是对所有随机候选的全局过滤器；
- `terminal_goals`：完整 seed 最终需要达到，但中间前缀可以尚未满足，例如 retain -> invalidate -> reuse；
- `preferences`：只影响趋向，不阻止 seed 作为 frontier；
- `forbid`：用户声明的一旦命中即拒绝的全局条件，例如不允许的 SQLSTATE 或危险 session 设置；通用语法/协议、capability 和资源边界分别由 ValidityPolicy、DialectCapabilities 和 SafetyBudget 管理，避免在每个 anchor 重复堆规则。

如果把所有目标都放进 must-have，生命周期 seed 在只生成 PREPARE 时就会被丢弃，系统永远无法演化到 ALTER 和 EXECUTE。

每条规则还必须声明来源和强度：

```cpp
enum class RuleStrength {
    HARD_POSTGRESQL, // 官方 PostgreSQL 语义、协议或已探测 capability
    HARD_SAFETY,     // 资源、沙盒、连接和不可恢复风险边界
    HARD_USER,       // 用户显式 invariant/forbid
    SOFT_HEURISTIC,  // 人工或统计启发式，只改变优先级
    OBSERVATION_ONLY // 只记录，不影响生成
};

enum class RuleDecision {
    ACCEPT,
    REJECT,
    UNKNOWN
};
```

只有前三类可以返回 `REJECT`。模型信息不足、parser 不覆盖某种 PostgreSQL 扩展、函数 volatility 未知或对象关系无法证明时返回 `UNKNOWN`，不能伪装成“不合法”。`UNKNOWN` 候选可以进入有预算的 legacy exploration/Quarantine 路径执行，执行成功后反向补充 observation；它不自动进入 guided hot archive。执行后的真实 SQLSTATE/成功结果仍计入对应 exploration lane 的观测合法率，但 UNKNOWN 本身不算一次语义失败。

所有 hard rule 必须有稳定 rule id、来源、适用 PostgreSQL 版本、单元测试和拒绝计数。运行指标发现某个非安全规则异常扩大拒绝率时，只能将其降级为 soft/observation 或关闭 guided mode，不能在线自动生成新的 hard rule。

锚点支持以下来源：

1. 结构锚点。

   例如至少两个 JOIN、包含窗口函数、相关子查询和 JSON 表达式。

2. 序列锚点。

   例如 retain -> invalidate -> reuse，且三个事件必须引用同一对象或依赖对象。

3. 示例 SQL 锚点。

   第一阶段可由用户显式描述其特征；支持稳定 SQL parser 后，再自动提取规范化 AST/IR 特征。

4. DBMS 子系统锚点。

   例如 PLAN_CACHE、CACHE_INVALIDATION、EXECUTOR_WINDOW。该类型锚点必须区分代理信号和实际观测证据。

5. 混合锚点。

   例如“语句必须成功执行，包含 window + aggregate，并优先产生新的 WindowAgg plan shape”。

AnchorCompiler 必须返回编译结果：

```cpp
struct AnchorCompileResult {
    AnchorCompileStatus status; // READY / UNSAT / UNSUPPORTED / DEGRADED
    CompiledAnchor anchor;
    int compiled_for_server_major;
    int compiled_for_server_version_num;
    std::vector<std::string> diagnostics;
    std::vector<std::string> relaxed_predicates;
};
```

处理原则：

- 谓词互相矛盾：标记 UNSAT，拒绝启动 guided mode；
- capability 不支持且不可降级：标记 UNSUPPORTED；
- 允许 relaxation：明确列出被放松项，生成新的 anchor version；
- 只有模糊 SubsystemTag：标记 DEGRADED，使用代理目标并降低置信度；
- 示例 SQL 无可用 parser：要求用户提供声明式特征 sidecar，不能用正则结果验证硬约束。
- anchor 引用了当前 PostgreSQL major 不支持的 syntax/EXPLAIN option 或不合法 transaction behavior：在运行前标记 UNSUPPORTED/UNSAT，不能等生成后用非法率“学出来”；
- server major、grammar hash 或 capability fingerprint 变化：重新编译 anchor，旧 compile result 不复用。
- SOFT_HEURISTIC 互相冲突：保留为多个探索方向或置零，不得把 AnchorCompileResult 变成 UNSAT；
- `UNKNOWN` 不是 capability UNSUPPORTED；只有官方语义或实际探测证明不可用时才拒绝。

### 6.4 AnchorPredicate

第一阶段需要支持的谓词：

    feature(HAS_JOIN)
    feature_count(HAS_JOIN) >= 2
    subquery_depth >= 2
    event(SQL_PREPARE)
    ordered_event(RETAIN_REFERENCE, INVALIDATION_TRIGGER, REUSE_REFERENCE)
    same_object(relation:t0)
    plan_node(WindowAgg)
    outcome(stage, event, transaction_phase).sqlstate_in(...)
    result_is_success
    complexity_between(min, max)

`invariants` 和 `forbid` 在所有可学习前缀上生效；`terminal_goals` 用于判断完整 anchor 是否达到；`preferences` 只影响距离和演化方向。

### 6.5 AnchorProgress

锚点评价器输出：

```cpp
struct AnchorEvaluation {
    bool invariants_satisfied;
    bool terminal_goals_satisfied;
    AnchorStage stage;
    double proximity;            // 0.0 ~ 1.0
    double progress_from_parent; // child proximity - parent proximity
    double confidence;           // 观测可靠度
    std::vector<std::string> satisfied_predicates;
    std::vector<std::string> missing_predicates;
};
```

主要演化信号使用：

    anchor_progress =
        proximity(child, anchor) - proximity(parent, anchor)

绝对 proximity 用于 seed 选择和归档，增量 progress 用于 credit assignment。

多步锚点的 proximity 首先由状态机阶段决定，再比较同阶段内的软目标，避免“添加很多无关复杂特征”超过真正完成 reuse 的 seed：

    stage score:
      START       0.0
      RETAINED    0.3
      INVALIDATED 0.6
      REUSED      0.9
      TERMINAL    1.0

只有相同或更高 stage 的 child 才能获得正的序列进度。低置信度 inferred evidence 不能推动终局 stage。

enum class SupportLevel {

    SUPPORTED,
    SUPPORTED_WITH_RESTRICTIONS

enum class TransactionBehavior {
    ALLOWED_IN_OR_OUT,
    REQUIRES_TRANSACTION_BLOCK,

## 7. 合法性内核

### 7.1 CatalogState

`CatalogState` 是生成器看到的逻辑 catalog，不要求实时镜像完整 DBMS catalog：

```text
Schema
  -> Table
       -> Column(name, type, nullable)
       -> Index
       -> Constraint
  -> View
  -> Function
  -> Temporary Object
```

它负责：

- 表、列、索引和函数的限定名；
- 对象存在性；
- 列类型和类型兼容；
- 受控 DDL 的 apply/rollback；
- prepared statement、view、cursor 对对象的引用关系；
- savepoint 对 catalog/session 状态的快照。

现有 `QueryInstantiatorData` 可以作为数据来源，但需要逐步避免以裸列名作为全局类型 key。

CatalogState 同时维护置信度：

    CATALOG_EXACT
      只执行了系统支持并成功 apply delta 的受控语句

    CATALOG_BEST_EFFORT
      执行成功，但包含尚未完全建模的非关键属性

    CATALOG_DIRTY
      cascade、未知 DDL、连接重置或执行结果不确定

GUIDED 模式只在 CATALOG_EXACT 或明确允许的 CATALOG_BEST_EFFORT 状态继续。进入 CATALOG_DIRTY 后立即终止当前 sequence，保存诊断并 reset；不要在未知 catalog 上继续生成并把后续错误归因给 learner。

对于 PostgreSQL 单条 DDL，可利用语句原子性：只有确认成功后才 apply delta。受控事务/savepoint 使用 CatalogState snapshot；不支持的任意 DDL 暂时只进入 legacy lane。

PostgreSQL 对象解析还必须区分：

- schema-qualified name 和依赖 `search_path` 的 unqualified name；
- permanent、unlogged 和 session-local temporary relation；
- relation name 与随表自动创建的 composite type name 的同 schema 冲突；
- identifier 的 quoted/unquoted 形态。

默认生成的内部对象名使用小写 ASCII、避免关键字并保持在默认 63 bytes 以内；只有 identifier/quoting 锚点才主动生成大小写敏感或需引用的名称。连接初始化时探测并记录 `max_identifier_length`，名称超过服务端实际限制时应在发送前拒绝，不能依赖服务端截断后再猜 CatalogState。

### 7.2 ScopeStack

每个 SELECT 层级维护独立 scope：

    当前可见 relation/alias
    每个 relation 的可见列
    outer query 引用权限
    当前 aggregate context
    当前 window context
    GROUP BY 支撑集合
    LATERAL 可见性
    输出列名和类型

至少实现：

- WHERE、JOIN ON、HAVING 输出 BOOL；
- LIMIT、OFFSET 输出 INT；
- CASE 分支求 common type；
- IN 两端类型兼容；
- SETOP 两侧列数一致且类型兼容；
- 非聚合 SELECT/HAVING 表达式受 GROUP BY 或 PostgreSQL 已识别的 functional dependency 支撑；首期仅把同表 primary key 纳入 functional dependency；
- window function 只允许进入该 query level 的 SELECT list 和 ORDER BY，不能进入 WHERE、GROUP BY 或 HAVING；普通 aggregate 可以成为 window function 参数，反向嵌套不允许；
- output alias 可在 ORDER BY/GROUP BY 使用，但不能在 WHERE/HAVING 使用；歧义时按 PostgreSQL 对 GROUP BY 与 ORDER BY 的不同解析规则处理；
- `FROM` subquery 只有显式 `LATERAL` 才能引用它之前的 FROM item；table function 参数即使省略 `LATERAL` 也可以引用之前的 item；LATERAL item 不能看到右侧尚未引入的 item；
- correlated subquery 显式记录 outer ref。

这里不能只做“输出类型正确”的局部检查。每个表达式节点还要携带 `query_level`、`clause_kind`、aggregate/window nesting state 和 lateral visibility frontier，repair 后重新跑完整 scope validation。

### 7.3 SessionState

生命周期类测试需要同一 backend session 的状态：

    transaction status
    savepoint stack
    prepared statement registry
    cursor/portal registry
    temporary object registry
    session settings and search_path
    plan_cache_mode
    backend pid
    server_version_num

PostgreSQL connector 每条 command drain 完成后，以 `PQtransactionStatus()` 为实际状态源：

    PQTRANS_IDLE     -> 可执行 DISCARD ALL 或开始下一事务
    PQTRANS_INTRANS  -> 位于可用事务块
    PQTRANS_INERROR  -> 失败事务，只允许生成预期恢复动作
    PQTRANS_ACTIVE   -> command 尚未 drain 完，不能开始下一 command
    PQTRANS_UNKNOWN  -> connection bad，session lost

一条错误在显式事务中通常会进入 aborted 状态，后续普通语句只会得到 `25P02`。若锚点不以 aborted-state 为目标，则只能执行 `ROLLBACK TO SAVEPOINT` 或 `ROLLBACK` 等恢复动作；恢复成功前不再生成普通 query，也不把连带的 `25P02` 计作独立生成失败。

prepared statement 只存在于当前 database session；cursor/portal 和 temporary object 也具有 session-local 语义。`PREPARE` 在其引用对象发生 definitional DDL、统计信息更新或 `search_path` 变化后可能被强制重分析/重规划。SessionState 因此必须记录 prepare 时的参数/结果类型、对象依赖、`search_path`、`plan_cache_mode`、custom/generic execution count；不能把 DDL 后的 `EXECUTE` 默认解释为“使用旧悬空计划”。

`plan_cache_mode=auto` 下 PostgreSQL 17 当前规则是前五次使用 custom plan，之后比较 generic plan 与 custom plan 平均估算成本再选择；`force_generic_plan` / `force_custom_plan` 可以覆盖该启发式。因此 prepared anchor 的第 1、5、6 次执行不是等价样本，必须把 execution ordinal 作为 scenario/feature 维度。

还有一个必须单独建模的边界：`search_path` 的值发生变化会触发重解析，但只是在路径前方新建一个同名对象、`search_path` 字符串本身不变时，服务端不一定立即重解析，因为原先依赖对象没有变化。该行为只能作为专门的 shadowing scenario，不能与普通 `search_path changed` trigger 共用 oracle。

连接断开、backend crash 或强制 reconnect 会丢失 prepared statement、cursor、临时对象和事务上下文。此时 SessionState 直接标记 DIRTY，不能从中断处续跑；恢复后必须从 scenario setup 和完整前缀重新 replay。

cursor registry 至少记录 `WITH HOLD`、`SCROLL/NO SCROLL`、声明事务和 query properties。`WITHOUT HOLD` 是默认值，不能跨成功 `COMMIT`；`WITH HOLD` 可跨 commit 留在同一 session，但不能与 `FOR UPDATE/FOR SHARE` 组合，并在创建事务 abort 时消失。把 `DECLARE -> COMMIT -> FETCH` 视为成功路径时必须显式生成 `WITH HOLD`，否则 oracle 应预期 `34000`，不能将两种路径混为同一锚点。

包含 volatile function 的 scrollable cursor 可能在回退重取时重新执行函数，不能用行值完全相等作为通用 oracle。默认 cursor scenario 对 volatile query 使用 `NO SCROLL`；专门测试 SCROLL/volatile 交互时只验证协议、SQLSTATE、行数边界和 session 存活，或使用 `SCROLL WITH HOLD` 在 commit 后读取其物化结果。

### 7.4 SchemaScenario

每个 scenario 包含：

- 确定性 DDL；
- 确定性数据 seed；
- NULL、重复值、边界值、倾斜值和相关分布；
- 普通、组合、表达式和部分索引；
- 可选 view、function、temporary object；
- `ANALYZE`；
- 对应 CatalogState；
- capability 要求；
- scenario fingerprint。

PostgreSQL 第一阶段建议：

    basic_join
    window_group
    correlated_subquery
    json_array
    index_expr
    lifecycle_prepare
    lifecycle_cursor
    transaction_savepoint

每个 scenario 还要固定并记录 plan/解析相关 session 设置：

    search_path = pg_catalog, <scenario_schema>, pg_temp
    TimeZone
    DateStyle
    IntervalStyle
    standard_conforming_strings
    plan_cache_mode
    jit

除专门测试 `search_path`/GUC 的锚点外，对象引用使用 schema qualification，并在每次 clean reset 后重新应用 canonical settings。temporary table 场景单独标注 `session_bound=true` 和 `ON COMMIT PRESERVE ROWS/DELETE ROWS/DROP`；PostgreSQL 省略 `ON COMMIT` 时默认 `PRESERVE ROWS`，与 SQL 标准默认 `DELETE ROWS` 不同，oracle 必须采用 PostgreSQL 语义。其 plan/statistics 不得交给另一连接观察，填充数据后按需在同一 session 手动 `ANALYZE`，不能等待 autovacuum 处理 temporary table。

scenario setup 是独立阶段，不参与 workload reward。每条 setup SQL 必须检查结果，任何失败都应终止当前样例，而不是无条件 append_good_stmt。

setup 采用两级验证：

1. 每条语句执行状态和 SQLSTATE 正常；
2. setup 结束后验证 scenario fingerprint，包括关键对象、列类型和必要行数。

连续 setup 失败达到阈值时进入 RECOVERING；如果相同 scenario 在干净 DBMS 上仍失败，禁用该 scenario 并降级到 basic_join，而不是持续重试。

隔离不能只有“每条都重建”一种昂贵模式。GenerationPlan 在执行前选择并固化 `IsolationProfile`：

    READ_ONLY_REUSE
      仅允许无 volatile/side effect、无 GUC/temp/prepare/transaction event 的 SELECT；
      校验 session/canonical-settings postcondition 后可复用预建 scenario。

    ROLLBACK_SANDBOX
      seed 本身不含 transaction-control 和 transaction-forbidden command 时，
      且不含 sequence、session advisory lock、session GUC、外部副作用或未知 volatility 时，
      用外层 BEGIN + seed + ROLLBACK 隔离 DML/受控 DDL。

    FULL_SCHEMA_RESET
      lifecycle、prepared、cursor、temp、显式 transaction-control 或不可安全回滚的场景。

    SERVER_RECREATE
      connection/backend fault、catalog/session DIRTY 或 database-level 场景。

`READ_ONLY_REUSE` 只是一项经过 whitelist 和 postcondition 证明的优化；一旦出现未知 function volatility、session setting 变化或 fingerprint 漂移，立即升级为 `FULL_SCHEMA_RESET`。不能为吞吐自动把 stateful anchor 降成只读复用。

需要 `FULL_SCHEMA_RESET` 时，clean reset 顺序固定为：

1. 确认没有 active command，并将所有 libpq result drain 到 null；
2. `PQTRANS_INTRANS/PQTRANS_INERROR` 时执行 `ROLLBACK` 并再次确认 `PQTRANS_IDLE`；
3. 在事务块外执行 `DISCARD ALL`，清除 prepared statements、cursor、temporary objects、cached plans 和 session GUC；
4. 在固定测试 database 中 `DROP SCHEMA <run_schema> CASCADE` / `CREATE SCHEMA <run_schema>`；
5. 应用 canonical session settings、执行 scenario setup 与 `ANALYZE`；
6. 校验 fingerprint 后清零 setup/observer trace bitmap；
7. 只有此后才接受并执行新 seed。

任一步失败都导致 connection/session 丢弃并进入 supervisor recovery；不得在未知 session 上只执行下一条 setup SQL。database 级重建是低频 `SERVER_RECREATE` 操作，不是 per-seed reset。各 isolation profile 分别统计吞吐、合法率和状态漂移率，防止只读快路径掩盖生命周期路径的成本。

## 8. 生成侧设计

### 8.1 三种 Generator Lane

#### Lane A：原始 RSG

保留当前随机 grammar 生成，提供探索和 baseline。生成选择不接受 anchor 正向要求、历史 reward 或 SOFT_HEURISTIC；执行前只应用协议/资源/沙盒 HARD_SAFETY、用户显式全局 forbid，以及能够由 PostgreSQL/capability 明确判定的 hard reject。模型无法判定时保留 UNKNOWN 探索，不能关闭该 lane。它有独立的最小采样概率，结果按 `legacy_exploration` 单独统计，避免其预期较低合法率污染 guided profile 的合法率保护线。

#### Lane B：受约束 RSG

扩展 RSG 接口，使其可以接收：

    required_ir_types
    preferred_ir_types
    forbidden_ir_types
    complexity_budget
    generation_context

其中 `required_ir_types` 和 `forbidden_ir_types` 只能来自 hard rule；人工偏好和历史经验只能进入 `preferred_ir_types` 或选择概率。禁止把“过去若干轮没成功”自动编译成 forbidden type。

可使用的策略：

- 根据目标 IR type 选择 reverse generation；
- 对已有合法 seed 做 targeted subtree mutation；
- 生成后进行 constraint check；
- 对名称、类型和作用域进行 repair；
- 有界 rejection sampling，超过次数后 fallback。

仅指定 `IRTypeSelectStmt` 不算受约束生成。

每次生成必须有 attempt budget，例如：

    generate attempts <= 10
    repair passes <= 3
    validation time <= configured budget

超过限制记录为 GENERATOR_EXHAUSTED，不执行候选 SQL，也不按 SQL 语义错误惩罚 learner。某个 profile 连续耗尽时触发 circuit breaker，在冷却窗口内改用 typed builder 或 legacy lane。

repair 只修改能定位的名称、类型、scope 或 PostgreSQL 规范性冲突，并记录修改节点比例。超过 `max_repair_ratio` 或必须把大部分树改成固定模板时放弃 repair，保留原始生成统计并重新探索；不能通过过度修补把不同随机输入都收敛为少数“合法标准答案”。

#### Lane C：Typed Directed Builder

针对合法率要求较高、事件关系明确的 QueryFamily 构造带类型的 IR 或安全字符串语句：

    JOIN_FILTER
    GROUP_AGGREGATE
    WINDOW_QUERY
    CORRELATED_SUBQUERY
    CTE_QUERY
    SET_OPERATION
    TYPE_FUNCTION_QUERY
    INDEX_PREDICATE_QUERY
    PREPARED_LIFECYCLE
    CURSOR_LIFECYCLE
    TEMP_OBJECT_LIFECYCLE
    TRANSACTION_STATE_LIFECYCLE

builder 优先输出现有 IR。对于 grammar/IR 暂不支持的 PREPARE、cursor 或过程语句，可以输出 `TYPESTRING`，但必须走统一安全接口，不得进入依赖 `stmt_ir` 的 RSG reward 路径。

对于 `TYPESTRING`：

- builder 同时输出 typed event/object metadata；
- 硬约束只使用 builder 可证明的 metadata 和结构化执行结果；
- regex 提取只能作为辅助诊断；
- 任意外部 SQL 字符串在没有 parser 时不得直接成为 mutation-eligible hot seed。

这样可以先可靠支持生命周期模板，同时避免假装已经具备通用 SQL 文本语义分析能力。

#### 随机性保护与选择混合

`ExplorationGuard` 每个 epoch 组合四个来源：

```text
legacy_random_floor          // 原始 RSG，不受经验压缩
uniform_profile_floor        // capability 可用 profile 的均匀探索
exploration_archive_floor    // 从 novelty reservoir 选择 parent
policy_remainder             // learner 对剩余概率的建议
```

这些 floor 配置必须非负且总和小于 1；启用 GUIDED 时 `legacy_random_floor` 和 `uniform_profile_floor` 必须大于 0。对 policy remainder 再应用 `max_profile_probability`，防止单一 profile 长期垄断。若 reservoir 暂时为空或 uniform 可用 profile 不足，对应预算回到 legacy/random；若候选 profile 只有一个，额外预算同样回到 legacy/random，而不是突破概率上限或交给唯一 profile。

策略每个 epoch 重新随机采样，多个同分项随机 tie-breaking，并周期性注入与当前 top profile 不同的 QueryFamily、ComplexityBudget 或 mutation operator。随机注入仍经过 HARD_POSTGRESQL/HARD_SAFETY/HARD_USER 检查，但不经过 SOFT_HEURISTIC 拒绝。

任何经验、checkpoint 或用户 soft preference 都不能修改三个探索 floor。只有用户显式关闭 GUIDED/某个 lane，或 capability/safety 证明其不可执行时，才允许概率为 0。

### 8.2 QueryFamily

QueryFamily 是高层生成意图，不等价于 statement type：

```text
WINDOW_QUERY
  requires: HAS_SELECT, HAS_WINDOW
  prefers: HAS_PARTITION_BY, HAS_ORDER_BY
  intended: OPTIMIZER_WINDOW, EXECUTOR_WINDOW

PREPARED_LIFECYCLE
  requires: ordered retain/related-trigger/reuse
  requires: related object refs
  intended: PLAN_CACHE, CACHE_INVALIDATION

CURSOR_LIFECYCLE
  requires: DECLARE/FETCH events and holdability-aware transaction path
  intended: CURSOR_PORTAL, TRANSACTION_STATE

TEMP_OBJECT_LIFECYCLE
  requires: same session and explicit ON COMMIT mode
  intended: CATALOG_MUTATION, TRANSACTION_STATE
```

### 8.3 ComplexityBudget

预算字段：

```cpp
struct ComplexityBudget {
    int statement_count;
    int sql_bytes;
    int ast_nodes;
    int join_count;
    int subquery_depth;
    int correlated_ref_count;
    int cte_count;
    int expr_depth;
    int function_count;
    int window_count;
    int aggregate_count;
    int type_family_count;
    int lifecycle_event_count;
    int dependency_span;
    uint64_t max_result_bytes;
    uint64_t max_rows_observed;
    uint64_t max_statement_time_ms;
};
```

预算不固定拉满，而是通过 curriculum 调整：

    合法率稳定
      -> 逐步提高一个或少数预算维度

    合法率跌破保护线
      -> 降低对应维度或切换到更安全 lane

有效复杂度评分需要抑制重复嵌套、无意义表达式和纯长度膨胀。

结果集大小和资源开销也是预算的一部分。复杂 SQL 可能语义合法但返回海量行，connector 不应把所有结果拼进 `res_str`。超过 `max_result_bytes` 或 `max_rows_observed` 后继续 drain protocol、停止保存行内容，并在 ExecutionResult 中标记 truncation；这不等价于 SQL 错误。

### 8.4 函数库

第一阶段使用静态、带签名的函数白名单：

```text
numeric:
  abs, mod, round, floor, ceil, greatest, least

string:
  length, lower, upper, substring, strpos, coalesce, nullif

timestamp:
  date_trunc, extract

json:
  jsonb_extract_path, jsonb_array_length, jsonb_typeof

array:
  array_length, unnest

aggregate:
  count, sum, avg, min, max

  row_number, rank, dense_rank, lag, lead
```

签名包含：

    parameter type families
    return type
    aggregate/window/scalar category
    volatility
    allowed clause
    dialect rendering

动态读取 `pg_proc` 可以后续增加，但不能替代生成期的类型约束。

### 9.1 ExecutionResult

connector 执行后返回或缓存结构化结果：

struct ExecutionResult {

    std::vector<ResultStatus> result_statuses;
    std::vector<int> native_result_statuses; // PostgreSQL: ExecStatusType numeric value

为减少跨 DBMS 一次性重构，可以先保留 `run_target()` 返回 fault code，同时增加 `last_execution_result()`；稳定后再统一接口。

### 9.2 PostgreSQL Connector 改造

1. 每个 `QueryStmt` 原样作为一个 command 发送，不做简单分号切分。主路径使用 `PQsendQueryParams(conn, sql, 0, ...)`，由 extended protocol 强制 single-command boundary；`PQsendQuery` 只留给明确测试 simple-query multi-command 语义的独立 legacy/compatibility lane。
2. 发送成功后、任何 `PQconsumeInput()`/`PQgetResult()` 之前，只调用一次 `PQsetSingleRowMode()` 或受版本保护的 chunked-row mode。调用失败时按 bounded full-result 路径执行或拒绝高结果量 query，不能在收到 `PGRES_TUPLES_OK` 后再次调用。
3. session 初始化时设置 `statement_timeout`；client watchdog 使用 nonblocking socket poll 驱动。
4. 遍历每个 `PGresult`，读取：

   - `PQresultStatus`；
   - `PQresultErrorField(..., PG_DIAG_SQLSTATE)`；
   - `PG_DIAG_SEVERITY_NONLOCALIZED`、primary message、detail、hint；
   - 可选 schema/table/column/datatype/constraint 字段；
   - command tag 和累计 row count。

5. 无论成功、`PGRES_FATAL_ERROR` 还是 cancel，都在独立的 bounded drain deadline 内持续读取并 `PQclear()` 每个非空 result，直到 `PQgetResult()` 返回 null。只有 drain 完成后才能读取最终 `PQtransactionStatus()` 并复用连接；client watchdog 到期或 bounded drain 失败时立即关闭该 `PGconn`、标记 session lost，绝不能在未 drain 的连接上发送下一 command。
6. 显式处理 `PGRES_COMMAND_OK`、`PGRES_TUPLES_OK`、`PGRES_SINGLE_TUPLE`、`PGRES_FATAL_ERROR` 和连接错误；COPY、pipeline、empty query、bad response 等未启用状态进入 UNSUPPORTED/OBSERVER 或 INFRASTRUCTURE 分类，不能误判为普通成功。
7. single-row/chunked mode 下可能先收到若干行再收到 fatal error；终局状态仍为失败，先前行只计资源消耗，不进入结果正确性或成功 reward。
8. `PQerrorMessage(conn)` 只用于 send/transport/connection 失败；statement 错误以对应 `PGresult` 的结构化字段为准，避免后续 libpq 调用覆盖 connection 上的最后错误文本。
9. timeout、连接断开和 backend crash 分开编码；SQLSTATE `57014` 还需结合 watchdog/cancel provenance 区分 `statement_timeout`、用户 cancel 和 supervisor cancel。
10. sequence 内保持同一 session；不同测试样例之间按 §7.4 的 `IsolationProfile` 复用、回滚或重置，不能由 connector 自行猜测。
11. 限制保存的结果内容、行数和错误文本长度，但仍完整 drain protocol，避免合法查询耗尽 fuzzer 内存或破坏下一 command 边界。
12. server wait/reconnect 使用有界退避和总时限，不能沿用无限 while/sleep。

timeout 使用双层保护：

- DBMS statement_timeout：处理正常可取消查询；
- client watchdog：处理 libpq、backend 或 server 无响应。

statement_timeout 后如果连接和事务仍可恢复，可以按策略 rollback；client watchdog、连接丢失或 backend crash 后 session 视为丢失，当前 sequence 必须停止并走完整 replay。无法判断是 timeout 还是 crash 时标记为 INFRASTRUCTURE/UNKNOWN，确认前不提供高 reward。

#### PostgreSQL SQLSTATE 分类

SQLSTATE 是五字符、非本地化的机器 oracle；error message 只用于诊断和同 SQLSTATE 内的低置信度细分。至少建立以下 versioned 分类：

| SQLSTATE/class | 含义 | 默认 FailureDomain/处理 |
|---|---|---|
| `00000` | successful completion | SUCCESS |
| `08` | connection exception | INFRASTRUCTURE 或候选 backend fault；session lost |
| `0A` | feature not supported | QUERY/CAPABILITY；仅在指定兼容性锚点可预期 |
| `22`、`23` | data/integrity error | QUERY；是否允许由具体 stage oracle 决定 |
| `25P02` | in failed SQL transaction | STATE_CONSEQUENCE；不重复惩罚后继 query |
| `25` 其他 | invalid transaction state | QUERY/STATE；按 transaction automaton 判断 |
| `26000` | invalid prepared statement name | QUERY/STATE；仅在指定 lifecycle stage 可预期 |
| `34000` | invalid cursor name | QUERY/STATE；结合 holdability/transaction phase 判断 |
| `40001`、`40P01` | serialization failure/deadlock | QUERY_RUNTIME；按并发场景重试/确认 |
| `42601` | syntax error | QUERY/PARSE |
| `42` 其他 | access、name、type、group/window 等 parse/analyze error | QUERY/ANALYZE，按 exact code 细分 |
| `53`、`54` | resource/program limit | 先检查预算与环境，再决定 QUERY 或 INFRASTRUCTURE |
| `55` | prerequisite state | QUERY/STATE；按对象和锁场景判断 |
| `57014` | query canceled | 结合 cancel provenance，不能自动当 DBMS fault |
| `57P01`~`57P05` | shutdown/connect/session termination | INFRASTRUCTURE 或候选 fault，session lost |
| `58` | system error | INFRASTRUCTURE/候选 fault，必须 replay |
| `XX` | PostgreSQL internal error/corruption | 高优先级 FaultArchive，重放后确认 |

`00000` 是统一模型中的 synthesized success code；成功 `PGresult` 不包含 error field，connector 应以 result status 判定成功，不能要求 `PQresultErrorField()` 返回 `00000`。

allowed SQLSTATE 必须绑定 `anchor_version + automaton_stage + SqlEvent + scenario_version`，不能只配置一个全局 set。error result 上 `PG_DIAG_SQLSTATE` 缺失通常表示 libpq 自身错误，此时不得退化为从本地化 message 猜 error class。

### 9.3 DecisionTrace

DecisionTrace 必须记录真正可学习的动作：

```cpp
enum class SelectionSource {
    LEGACY_RANDOM_FLOOR,
    UNIFORM_PROFILE_FLOOR,
    EXPLORATION_ARCHIVE_FLOOR,
    POLICY_REMAINDER
};

struct DecisionTrace {
    std::string campaign_id;
    std::string run_id;
    uint32_t core_id;
    uint64_t epoch_id;

    std::string dbms;
    std::string anchor_id;
    std::string schema_scenario;

    GeneratorLane lane;
    SelectionSource selection_source;
    std::string strategy_profile_id;
    uint64_t policy_snapshot_version;
    QueryFamily query_family;
    SqlEvent stmt_event;
    IsolationProfile isolation_profile;
    ComplexityBudget budget;

    uint64_t random_seed;
    SeedId parent_seed_id;
    int statement_index;
};
```

`SelectionSource` 至少区分 `LEGACY_RANDOM_FLOOR`、`UNIFORM_PROFILE_FLOOR`、`EXPLORATION_ARCHIVE_FLOOR` 和 `POLICY_REMAINDER`，否则无法审计 learner 是否实际侵占了随机预算。DecisionTrace 保持固定字段数和字符串长度上限，只记录最终 learner 真正选择和归因的 profile/lane/family/budget。

完整 grammar production、mutation target 和 anchor-preserving action 进入独立、长度有界的 `GenerationRecipeV1`，只为被 archive 接纳并需要 rehydrate 的 seed 保存；普通 observation 不写这类向量。该结构是运行时表示，写入 `ObservationRecordV1` 时 lane/profile/family/event 必须转换为稳定文本 id；`policy_snapshot_version`、计数和 seed id 按 §13 的无损整数规则编码。

### 9.4 FeatureVector

热路径内部使用固定结构和 bitset：

```cpp
struct FeatureVector {
    SqlFeatureBits sql_features;
    NumericFeatures numeric;

    std::vector<SqlEvent> event_trace;
    std::vector<ObjectRef> object_refs;
    std::vector<SubsystemEvidence> subsystem_evidence;

    uint64_t normalized_ast_hash;
    uint64_t semantic_feature_hash;
    uint64_t sequence_hash;
    uint64_t plan_shape_hash;
};
```

不要直接对 unordered_map 遍历结果计算 hash。

FeatureVector 同样是可重建的运行时缓存。持久化时只保存必要的原始 observation 和带 extractor/normalizer/hash 版本的可选缓存；`bitset` 位序、vector 内存布局和当前 hash 值都不是跨版本 API。

### 9.5 规范化与多样性

至少维护四类 novelty：

1. normalized structural novelty。

   标识符、普通字面量和无关 alias 归一化后计算 IR/AST hash。

2. semantic feature novelty。

   比较 SqlFeature、复杂度和类型组合，可使用频率反比或 k-nearest distance。

3. sequence novelty。

   事件自动机路径、对象关系图和 event n-gram。

4. runtime novelty。

   plan shape、coverage bucket、SQLSTATE 和规范化错误签名。

“是否出现过”的 bool 只用于 feature presence，不能单独承担 novelty；最终实现以 versioned structural/semantic hash、有限计数和 reservoir 去重计算多样性，不再引入无界历史距离模型。

### 9.6 CoverageObservation

当前 `has_new_bits()` 会更新全局 virgin bitmap，不能在 RewardCalculator、AFL 保存和日志逻辑中重复调用。

建议单次采集：

```cpp
struct CoverageObservation {
    uint8_t afl_novelty;      // 0/1/2
    uint32_t new_edge_count;
    uint64_t trace_hash;
};
```

执行后由统一 observer 调用一次，再把结果传给 AFL 保存和学习模块。

AFL bitmap 可能受到 map collision、后台进程、并发活动和非确定执行影响。首次出现的新 coverage 先标记 UNCONFIRMED；普通 seed 可以保存，但只有重放后稳定出现，或同时存在强语义/plan 信号时，才作为较强 learner reward。

当前 PostgreSQL target 与 AFL 使用共享 trace bitmap，不能把“隔离 bitmap”当作已经存在的能力。首期确认流程必须串行化：保存候选 trace snapshot/hash，清零 trace bitmap，重放 setup + 完整 sequence，比较候选 edge 子集/trace hash，并且不再次调用会消耗主 virgin map 的 `has_new_bits()`。若同一 server 仍有后台覆盖噪声，则 confirmation 保持 LOW_CONFIDENCE；后续才可增加独立 instrumented instance 或独立 shared-memory map。plan observer 同样不得与目标 command 并发使用该 bitmap。

### 9.7 Query Plan

plan observer 独立于纯 parser：

    successful SELECT
      -> 按采样率判断
      -> 独立连接或隔离执行
      -> EXPLAIN (FORMAT JSON, COSTS OFF, SUMMARY OFF)
      -> 解析 plan node tree
      -> 规范化 relation/index/object name
      -> 生成 histogram 和 shape hash

`TIMING` 只能在 `ANALYZE` 时使用，因此非执行 observer 不能发送原方案中的 `TIMING OFF`。默认不使用 `ANALYZE`，避免二次执行 volatile 或有副作用的查询；即使包在 `BEGIN/ROLLBACK` 中，volatile function、外部副作用、锁和序列值也不一定可由 rollback 消除。DDL、事务和 cursor 锚点不强制 plan。

PostgreSQL 17 的 `EXPLAIN (GENERIC_PLAN ON, FORMAT JSON, ...)` 可以为带 `$1` 参数的可预备语句生成 generic plan，且不能与 `ANALYZE` 同用。它用于结构代理，不等价于某个 live prepared statement 实际选择的 generic/custom plan。实际选择应在同一 replay session 中结合 `EXPLAIN EXECUTE` 以及 `pg_prepared_statements.generic_plans/custom_plans` 观察。

即使 DDL 前后 plan shape 改变，也只能证明“选择到的 plan 发生变化”；plan shape 不变也不能证明没有重规划。`pg_prepared_statements` 暴露的是 generic/custom plan 被选择的次数，不暴露 invalidation counter。因此没有专门 instrumentation 或稳定 coverage 映射时，`CACHE_INVALIDATION` 最高只能标记为 `SEMANTIC_ORACLE`，不能伪报为直接 `OBSERVED`。

plan observer 的覆盖不能混入被测 SQL 的 coverage observation。在当前共享 bitmap 架构下调度必须串行：执行主 command -> 采集主 trace snapshot -> 执行可选 plan observer -> 丢弃/清零 observer trace -> 才允许下一主 command。若无法保证没有并发 observer/backend 活动，则关闭 plan-derived coverage，只保留 JSON plan 信号。

### 9.8 PlanEligibility

“独立连接采集 plan”并非对所有 SQL 都可行。独立连接看不到：

- 当前事务尚未提交的 DDL/DML；
- temporary table；
- prepared statement；
- cursor/portal；
- session-local GUC 和角色状态。

因此先判断：

```cpp
enum class PlanEligibility {
    SEPARATE_SESSION_SAFE,
    SAME_SESSION_REQUIRED,
    UNSUPPORTED,
    SKIP_VOLATILE_OR_EXPENSIVE
};
```

首期只对 `SEPARATE_SESSION_SAFE` 的、无副作用且只引用全局可见对象的成功 SELECT 采集 plan。`SAME_SESSION_REQUIRED` 在 live fuzzing session 默认跳过，因为同 session `EXPLAIN EXECUTE` 会增加 prepared statement 执行/计划计数，可能改变前五次 custom plan 与后续 generic/custom 选择，observer 本身就会改写被观测状态。

prepared anchor 如确需 plan 证据，使用 diagnostic replay session：从干净 scenario 重放完整前缀，在指定 observation point 查询 `pg_prepared_statements`，再执行 `EXPLAIN EXECUTE`。该 replay 的 coverage 和 plan counter 不回写主 seed 的执行观察。cursor/temporary-object 锚点同理只能在完整同 session replay 中观察，不能把主 session 的 prepared/cursor/temp 状态复制到另一连接。

plan hash 受 statistics、GUC、PostgreSQL build、数据规模、prepared execution ordinal 和 generic/custom mode 影响，只能在相同 scenario fingerprint、plan-relevant settings、server major/build id 及同类 observation mode 内比较。首次新 plan shape 可进入候选 novelty，重复执行稳定后再提升置信度。

### 9.9 FeedbackMapper 的职责

不建议把全部新逻辑塞进现有空 `FeedbackMapper`。可以让它成为兼容 facade，内部组合：

    FeatureExtractor
    EventExtractor
    ObjectRefExtractor
    SubsystemMapper
    AnchorEvaluator

执行 SQL、收集 plan 和更新 learner 分别由其他模块负责，以便单元测试。

## 10. 准入、评分与奖励

### 10.1 AdmissionGate

准入拆成两层，避免“必须接近当前锚点”反过来清空随机探索样本。

所有正常 archive 候选先通过 `SafetyValidityGate`：

1. scenario setup 成功；
2. PostgreSQL hard rule、全局 user forbid 和 ValidityPolicy 满足；
3. DBMS 连接存活；
4. 没有超出绝对安全预算；
5. 可以生成完整 reproducer。

`AnchorAdmissionGate` 再检查当前 AnchorSpec 的正向 invariants、状态机 stage 和 terminal goals。它只决定候选是否有资格进入当前锚点的 Completed/Frontier，而不决定一个已执行有效、结构新颖的随机样例是否可进入 ExplorationArchive。这样“必须包含 window/prepare/cursor”等定向要求不会被误用成全局语法禁令。当前 `forbid` 语义固定为全局约束，不支持隐式 lane scope。

根据 anchor 状态进入不同区域：

- CompletedArchive：terminal_goals 已满足；
- FrontierArchive：invariants 满足、前缀有效，且状态机取得进展；
- ExplorationArchive：通过 SafetyValidityGate 且具有结构/feature/coverage 新颖性，但可以不满足当前锚点的正向 invariants；
- Quarantine：观测不完整、模型可能漂移或结果尚未确认；
- FaultArchive：已确认或待确认的 crash/assert/sanitizer；
- Drop：无进展的普通失败或不可恢复数据。

FrontierArchive 是多步锚点可行性的关键。它按 anchor stage 设置有限 beam width 和 TTL；长期没有后继进展的前缀会被淘汰，避免大量 PREPARE-only seed 占满内存。

ExplorationArchive 使用有界 reservoir sampling，而不是按人工 cell 规则只保留“看起来有用”的结构。它只保存少量执行有效、非重复样例，并保留固定 parent sampling floor；即使某个 seed 与当前锚点距离较远，也可能通过后续大步 mutation 提供当前模型未预见的路径。未通过 AnchorAdmissionGate 的 seed 标记 `anchor_eligible=false`，不能直接作为当前 guided path 的已达标父本；只有 mutation 后重新通过 gate 才进入 Frontier/Completed。切换 anchor 后可重新评价这些 seed，但不沿用旧 reward。

`RuleDecision=UNKNOWN` 且执行成功的候选先进入 Quarantine 或 ExplorationArchive，只有结构化 importer/metadata 足以支持安全 mutation 后才升级为 HotSeed。其实际成功/失败可以更新对应 lane/profile 的结果统计，但不能从单个 UNKNOWN 结果泛化出“所有未知结构都应减少”的负向规则。

### 10.2 ScoreVector

```cpp
struct ScoreVector {
    double anchor_proximity;
    double anchor_progress;
    double effective_complexity;
    double structural_novelty;
    double sequence_novelty;
    double runtime_novelty;
    double coverage_novelty;
    double execution_cost;
};
```

ScoreVector 不再包含 validity：合法性由 SafetyValidityGate 和分层合法率保护线处理，不能被其他高分抵消。其余分量由当前 AnchorEvaluator、FeatureExtractor 和 normalization 配置派生，只用于当前 run 的归档选择和显示。磁盘可缓存其数值及 `score_schema_version`，但恢复后不得直接用于 policy、cell 排名或准入；版本不完全匹配时必须重算。

最终归档使用固定 cell 和字典序准则，不实现通用 Pareto dominance，以保持容量、选择和跨版本重分 cell 的行为可解释。

### 10.3 Policy RewardProjection

learner 需要比较 profile 时，使用归一化、截断后的临时投影：

```text
reward =
    confidence * (
      w_anchor   * clip(anchor_progress)
    + w_novelty  * clip(novelty)
    + w_complex  * clip(effective_complexity_delta)
    + w_coverage * clip(confirmed_coverage_novelty)
    + w_runtime  * clip(confirmed_runtime_novelty)
    )
  - w_cost     * normalized_cost
```

前提是 SafetyValidityGate 已通过。无效 SQL 不参与正常正奖励竞争；anchor proximity/progress 只有在 AnchorAdmissionGate 的对应 stage 可评价时才计入，未达标的 ExplorationArchive seed 只保留 novelty/coverage 等独立观测，不能伪造 anchor 正奖励。

初始权重不应直接写死为永久常量，建议配置化并记录版本。

各维度使用预定义范围或按 anchor/scenario 隔离的在线统计进行缩放，最终截断到有限区间。不要直接把 +200 crash 与普通 reward 混合；未确认 fault 进入 FaultArchive，重放确认后只给 profile 一个有上限的稀有事件信号，避免一次 flaky crash 永久污染策略。

RewardProjection 只能影响 `policy_remainder`，不能改变 ExplorationGuard 的 floor、hard-rule 判定或 FaultArchive 保存。负 reward 也只能在有限窗口内降低 profile 的剩余概率，不能创建永久 blacklist；capability/safety 仍允许的 profile 在后续轮次始终保留重新被抽中的机会。

### 10.4 预期错误

生命周期锚点的 reuse 阶段可能产生正常结果，也可能产生场景明确定义的优雅错误，但不能先假设“对象变化后一定使用旧缓存计划”。

例如：

    PREPARE p AS SELECT * FROM t0;
    ALTER TABLE t0 ADD COLUMN x int;
    EXECUTE p;

按 PostgreSQL 17 语义，prepared statement 引用对象发生 definitional DDL、statistics 更新或 `search_path` 改变后，服务端可能强制重分析/重规划。因此上例的默认成功 oracle 应是“`EXECUTE` 成功且 prepared statement 仍存在”；只有特意构造语义不再兼容的变体，才允许 scenario oracle 中列出的 exact SQLSTATE。错误文本签名不能单独把任意失败升级为 EXPECTED_OUTCOME。

allowed SQLSTATE 只在指定 anchor stage、statement event、transaction phase、server major 和 scenario version 上生效。同一个 SQLSTATE 出现在 PREPARE 阶段或不相关语句上仍属于失败。只匹配错误文本而没有稳定 SQLSTATE 时不得满足硬 terminal goal，只能进入低置信度诊断并要求重放确认。

### 10.5 Credit Assignment

单条语句反馈：

- 更新所属 StrategyProfile 的合法、进度、novelty 和成本计数；
- grammar/mutation action 只进入候选期的有界 recipe trace；普通 observation 丢弃，入档 seed 才固化为 GenerationRecipe。现有 RSG MAB 可在 LEGACY 内继续运行，但不与新 learner 交叉回传 reward。

序列终局反馈：

- reuse 阶段成功时，只向生成 RETAIN、INVALIDATE、REUSE 对应语句的 StrategyProfile 决策回传 credit；
- 使用 eligibility trace 或固定衰减；
- 对无关对象事件不回传对象关系奖励。

当前 RSG 将一次结果平均奖励给树上所有 grammar expression，只能留在 legacy 路径，不能作为跨轮统计或新 StrategyProfile 的 credit。

## 11. LearningController

### 11.1 最终 StrategyProfile

直接实现多层 contextual bandit 会同时引入大量不可独立验证的状态和信用分配问题。最终实现使用小型、配置化的 `StrategyProfile` 集合：

```cpp
struct StrategyProfile {
    std::string stable_id;
    GeneratorLane lane;
    QueryFamily family;
    BudgetLevel budget;
    MutationPolicy mutation;
};
```

例如：

    legacy_random
    typed_window_low
    typed_join_medium
    mutate_anchor_preserving
    lifecycle_prepare_safe
    lifecycle_cursor_safe

AnchorCompiler 和 capability mask 先过滤不可用 profile，learner 只在剩余的有限集合中选择。这比为 scenario、family、budget、function 和 grammar rule 同时建 arm 更容易稳定验证。

最终交付不再单独配置第二个 epsilon。`uniform_profile_floor` 已承担强制均匀探索；learner 只对 `policy_remainder` 按有界经验分数排序分配，最高项受 `max_profile_probability` 限制，溢出依次分给其他可用 profile，同分随机打散。样本不足时 policy remainder 也使用均匀分布：

```cpp
struct RunProfileStat {
    uint64_t attempts;
    uint64_t valid_attempts;
    uint64_t terminal_hits;
    double mean_reward;
    double recent_reward;
    double valid_rate;
    double anchor_progress_rate;
    double terminal_hits_per_valid_million;
    double novelty_rate;
    double timeout_rate;
    double infra_failure_rate;
    double mean_cost_us;
    double confidence;
};
```

必须处理：

- 未尝试 profile 由 uniform floor 覆盖；
- 多个最高分 profile 的随机 tie-breaking；
- reward 衰减，避免早期偶然结果永久主导；
- anchor、dialect、scenario 之间的统计隔离；
- 用户切换锚点时不污染新策略；
- infrastructure/observer failure 不进入 attempts 和 mean_reward；
- 样本量不足时使用保守先验，不把 1/1 成功视为稳定高分。
- learner 输出只作为 `policy_remainder`，必须经过 ExplorationGuard。

### 11.2 学习范围边界

当前 learner 的唯一选择单元是有限 `StrategyProfile`，不再拆成 lane/scenario/family/budget/grammar 多层，也不把 CatalogState、父 seed 高维特征或任意 context 写入策略。profile 集合变化必须增加 `generator_profile_set_version`；旧 profile 统计只有在稳定 id 仍存在且 §13 判为 `EXACT_RESUME` 时才可映射。分层 contextual bandit 或 grammar-rule learner 需要另立方案和数据合同，不属于本次最终实现。

### 11.3 合法率保护与 curriculum

每个 family/budget 维护合法率窗口：

    valid_rate 高且稳定
      -> 尝试提高一个预算维度

    valid_rate 下降
      -> 降低预算或选择 typed builder

    anchor progress 停滞
      -> 增加 exploration 或切换 mutation operator

保护逻辑使用滞回和最小样本数，避免合法率在阈值附近反复升降预算。连续多个窗口异常才降级；恢复也需要多个稳定窗口。

### 11.4 Shadow 更新与策略回滚

GUIDED 前先运行 GUIDED_SHADOW：

- 记录 learner 本来会选择的 profile；
- 实际仍执行 legacy/固定 profile；
- 离线检查 reward、合法率和选择分布；
- 确认没有 infrastructure 信号污染后才允许影响生成。

每个 run-local policy snapshot 记录 anchor/scenario/build/grammar hash，只保存在当前进程的双缓冲选择表中。新 snapshot 先经过 canary 时间窗；合法率、吞吐或 replay rate 越过保护线时自动回滚到上一个稳定 snapshot，并进入冷却期。它不是 §13 的跨轮 checkpoint，重启后不恢复。

### 11.5 ExplorationGuard 与 epoch 更新

主执行热路径不在每条 SQL 后重建策略分布。每条 observation 只追加固定大小的计数增量；满足 `policy.update_every_candidates` 或 `policy.update_every_ms` 后，由 controller 在 epoch 边界批量更新：

1. 合并本 epoch 的成功、合法、stage transition、terminal hit、novelty、timeout 和 cost；
2. 更新 run-local recent window；
3. 计算 policy remainder；
4. 由 ExplorationGuard 应用探索下限、单 profile 上限和 capability/safety mask；
5. 原子发布下一 epoch 的只读选择表。

生成线程只读取选择表并使用线程/进程本地 PRNG 抽样，不能在热路径持有 checkpoint/archive 全局锁。epoch observation buffer 有固定容量；溢出时合并同类计数或丢弃低价值明细，但不得阻塞 SQL 执行、丢失 confirmed fault 或改变 ExplorationGuard floor。

ExplorationGuard 持续监控：

    actual legacy/random fraction
    uniform profile exploration fraction
    maximum profile share
    selection entropy
    repeated-template ratio

任一指标连续低于保护线时，不继续“学习修正学习器”，而是冻结 policy update、恢复稳定 mixture 或进入 SAFE_FALLBACK。探索下限属于配置/安全合同，不能由 learner 自调。

### 11.6 CampaignState：最小跨轮经验

需要明确区分两个生命周期：

```text
CampaignState  // 当前进程加载的跨轮只读视图，由 checkpoint 构建
RunState       // 当前进程轮次，快变量，进程退出即失效
```

`CampaignState` 是内存中的只读统计视图，不是直接序列化的 C++ 对象。磁盘 checkpoint 只保存可解释、可交换合并的原始计数；代表 seed 由独立 `ArchiveManifest` 管理，避免统计恢复与复杂 seed 恢复互相拖累：

```cpp
struct CampaignCheckpointRecordV1 {
    CompatibilityFingerprintRecord compatibility;
    DecimalU64 checkpoint_sequence;

    std::vector<ProfileStatRecordV1> profiles;
    std::vector<StageTransitionStatRecordV1> stage_transitions;
};
```

`ProfileStatRecordV1` 只包含稳定 profile id、attempts、valid attempts、各 stage 到达/转移次数、terminal hits、timeout count 和总执行成本。它不保存或重建完整 `mean_reward`；跨轮 prior 只依据这些稳定率和成本摘要，复杂度、novelty、coverage 等派生 reward 仅由当前 run observation 计算。最终格式不持久化任意高维 context、动态特征权重、负样本规则、在线归一化分布或每条普通 SQL 历史。

profile/stage 使用稳定、带 namespace 的文本 id，例如 `profile.pg.window.typed.v1`，不得持久化 C++ enum ordinal。加载时对已知 id 建立当前运行时索引，未知 id 按条跳过并记录诊断，不能因未来版本多出一个 profile 拒绝整个 checkpoint。记录列表有独立条目和字节上限；SQL 文本、structural hash、错误消息和任意动态字符串不得成为统计 key。

以下状态都只属于当前进程，重启后必须重建或清空，但所有权不能混在一起：

- `RunState`：recent reward/validity window、epoch counters、cooldown、临时 profile 排名和只读选择表；
- `ExecutionContext`：CatalogState、SessionState、connection/backend id；
- `EvolutionArchive`：HotSeed/SeedRuntime、IR 所有权和内存 novelty cache；
- `ObservationPipeline`：未确认 coverage、plan、timeout/fault、本轮 normalization 和 observation backlog；
- core-local runtime：PRNG 状态和临时 recipe trace。

跨轮 warm start 使用有界先验：

```text
prior_attempts = min(
    campaign_attempts * age_decay,
    experience.max_prior_pseudo_attempts)

effective_stat = combine(prior_stat, current_run_stat)
prior_weight <= experience.max_prior_weight
```

`age_decay` 以累计候选数/有效执行数或墙钟时间计算并写明口径，不能简单按“重启次数”衰减，否则内存问题造成的频繁短 run 会无意义地快速遗忘。

新 run 在 `experience.min_fresh_attempts` 前只允许低权重 warm start 并保持强制探索，不能启动即完全服从旧策略；达到 fresh sample 门槛后也只能增加到 `max_prior_weight`。当前轮积累足够样本后 recent window 可以在有界时间内推翻历史均值。历史负 reward 只会降低有上限的 prior，不产生永久 blacklist；所有可用 profile 仍受 uniform exploration floor 保护。

Campaign 加载统一遵循 §13.1 的格式可读性和语义复用判定。对 learner 而言只有 `EXACT_RESUME` 可以加载衰减、封顶后的统计 prior；`REPLAY_AND_REEVALUATE` 和 `REPLAY_ONLY` 默认 prior 为 0。用户切换 anchor 时可以重新评价 ExplorationArchive seed，但不继承旧 anchor reward 和 stage transition 统计。判定结果必须写入新 run 元数据，不允许静默“尽量加载”。

### 11.7 稀有终局目标与两阶段启用

对于需要大量随机尝试才偶尔命中的目标，不能只优化平均 reward。每个 profile 额外记录：

    valid attempts per second
    each anchor stage reach rate
    stage A -> B transition rate
    terminal hits per valid million
    statements/time to first terminal hit

proximity/progress 继续为稀疏终局提供 shaped feedback，但 terminal hit 始终作为独立统计，不能被大量“接近但永不到达”的高 proximity seed 淹没。学习算法保持有限 StrategyProfile + guarded greedy remainder；终局稀疏通过 stage 计数、archive 和大样本积累处理，不在本方案中再引入 Thompson/UCB 或高维模型。

实现顺序强制分两步：

1. 先运行纯 run-local learner，证明随机下限、吞吐和回滚稳定；
2. 再启用 `campaign.enabled`，先只加载 archive seed，最后才以小 `max_prior_weight` 启用统计 warm start。

任一步没有通过 A/B 与 restart 测试，就保持下一步关闭。跨轮经验不是 GUIDED 的前置条件，禁用后仍能使用轮内学习。

### 11.8 经验机制的准入与删除标准

经验模块本身也必须接受“是否值得存在”的验证，不能因为设计上更智能就默认长期启用。新增一个持久化统计维度、context 或策略层前必须同时满足：

1. key 空间有限且有独立容量上限；
2. 能在 GUIDED_SHADOW 中单独观察其决策影响；
3. 与 archive-only、run-local learner 和完全冷启动三个基线做消融对比；
4. 在多随机种子、重启和错误先验测试中，terminal hit 分布或到达关键 stage 的成本有稳定收益；
5. 不越过合法率、多样性、随机 floor、吞吐、内存和写盘保护线；
6. 能通过单一 feature flag 关闭，关闭后不改变 seed 格式和基本 replay 能力。

若“恢复代表 seed、重新评分”已获得主要收益，而统计 prior 没有显著增益，就只保留 archive warm start，不上线 policy warm start。若某个经验维度连续多个评估周期无收益、难以解释或导致干扰，则从 checkpoint schema 中删除，而不是继续增加补偿规则。最终格式禁止持久化 grammar-rule 级概率、任意 context embedding、失败 SQL 黑名单和动态硬规则。

## 12. EvolutionArchive 与序列队列

### 12.1 运行时所有权模型

最终 `QuerySequence` 只维护一个 `StmtRuntime` 容器；每个 slot 同时拥有 statement 和对应元数据，不再维护 `v_all_query_stmts`、`v_good_query_stmts`、`statement_meta` 三份平行数组：

```cpp
enum class RehydrationKind;

struct StmtRuntime {
    std::unique_ptr<QueryStmt> statement;
    std::string rendered_sql_cache;
    DecisionTrace decision;
    ExecutionResult execution;
    FeatureVector features;

    bool required_for_reproducer;
    bool mutation_eligible;
    bool expected_failure;
    bool catalog_effect_applied;
};

struct SeedRuntime {
    SeedId id;
    std::optional<SeedId> parent_id;
    std::string anchor_id;
    std::string dialect;
    std::string scenario_id;

    std::unique_ptr<QuerySequence> sequence; // 内部唯一 StmtRuntime 容器
    FeatureVector sequence_features;
    AnchorEvaluation anchor_evaluation;
    ScoreVector score_cache;

    bool reproducible;
    bool anchor_eligible;
    bool mutation_eligible;
    RehydrationKind rehydration_kind;
    size_t estimated_memory_bytes;
};
```

QueryStmt 使用唯一所有权，任何 good/mutation-eligible 列表都是 index/view，不能复制对象。迁移期可以从旧双 vector 构造该容器，但最终不得双向同步。`rendered_sql_cache`、feature、evaluation 和 score 都可重建；`SeedRuntime` 禁止直接 dump/serialize，跨轮只使用 §13 的 `SeedArtifactV1`/`ReplayBundleV1`。

### 12.2 Hot/Cold Seed

IR 深拷贝成本较高，不能让磁盘 archive 中所有 seed 都常驻内存：

- HotSeed：内存中保留 QuerySequence/IR，可以直接 mutation；
- ColdSeed：内存中只保存 `SeedArtifactV1` 引用和少量索引字段，不持有完整 IR/feature/score；
- 每个 cell 只有少量 HotSeed；
- ColdSeed 只有在具备语义版本匹配的 GenerationRecipe、可靠 SQL->IR importer，或同 build/同 IR ABI 的 cache 时才能重新变为 mutation-eligible；
- 达到全局内存上限后按 cell 最低优先级降为 ColdSeed，不依赖操作系统 OOM。

```cpp
enum class RehydrationKind {
    IR_CACHE_EXACT,
    GENERATION_RECIPE,
    SQL_IMPORT,
    SEED_REPLAY_ONLY
};
```

长期权威内容始终是完整 replay records；GenerationRecipe 仅在 generator/grammar 语义版本兼容时用于重建。`IR_CACHE_EXACT` 是同 build/同 IR ABI 的加速缓存，不属于跨版本承诺，任何 ABI/hash 不匹配都直接忽略。只有 rendered SQL 的 ColdSeed 在 importer 未完成时标记 `SEED_REPLAY_ONLY`，仍可重放、重新提取 feature 和重新评分，但不能假装延续原 lineage 做结构 mutation。单个 seed 加载失败只降级该 seed，不影响统计 checkpoint 或其他 artifact。

### 12.3 Archive 策略

最终使用 anchor 隔离的固定网格：

```text
cell dimensions:
  query/event family
  anchor stage
  coarse complexity bucket
```

默认每个 cell 最多 4 个 HotSeed：

- 最高 anchor proximity seed；
- 最高 novelty seed；
- 最低执行成本 seed；
- 最新 coverage seed。

维度和 bucket 必须是有限枚举，不能把任意 structural hash 直接作为 cell key。结构 hash 用于 cell 内去重和 novelty。cell id、旧 score 和旧 novelty 排名都只是当前版本缓存，不作为跨版本权威数据；恢复 seed 时用当前 extractor/anchor 重新分 cell 和排序。全局设置 max_cells、max_hot_seeds、max_memory_bytes 和 max_disk_bytes。

FrontierArchive 按 anchor stage 维护 beam，每个 entry 有最大后代尝试数和 TTL。CompletedArchive、FrontierArchive、ExplorationArchive、FaultArchive 和 Quarantine 分开计费，fault 结果不能挤掉正常演化 seed。

固定网格是 guided archive，不负责覆盖所有随机变数。ExplorationArchive 另用有界 reservoir，按有效候选流进行抽样并对 normalized hash 去重，不要求命中预定义 family/cell。它拥有独立内存/磁盘配额和 parent sampling floor，learner 不能用低 reward 淘汰整个 reservoir。

跨轮只保留每个 guided cell 的少量代表、reservoir 样本、可重放 terminal/fault 和仍有 TTL 的关键 frontier；不保存全部普通历史。archive compaction 在后台按稳定快照执行，达到预算时优先丢弃不可重建、重复、低置信度 observation，而不是扩大主进程内存等待 OOM。

### 12.4 与现有 FuzzingSequenceQueue 的关系

迁移阶段不直接删除 `FuzzingSequenceQueue`：

- 修复除零、tie 和所有权问题；
- 保留原 round-robin 模式作为 baseline；
- 新增 `EvolutionArchive` 作为学习模式的数据源；
- learning disabled 时完全使用旧路径；
- learning enabled 时从 archive 选择 parent，再复用现有 mutation。

稳定后再逐步合并接口。

parent 只能从相同 dialect、DBMS build、grammar hash、scenario version 和兼容 anchor version 中选择。任何不兼容 seed 只能重放分析，不能直接跨上下文 mutation。

### 12.5 AFL queue 与完整序列

AFL queue 和 learning archive 用途不同：

- AFL queue 继续保存与 bitmap 对应的输入；
- learning archive 保存完整状态化序列；
- crash/reproducer 必须包含 scenario setup 和完整 session 顺序；
- 不把包含过程体的完整 sequence 交给简单分号 splitter。

## 13. 持久化与重放

### 13.1 唯一持久化模型

持久化层不复用 `SeedRuntime`、`StmtRuntime`、`QuerySequence`、`FeatureVector`、`ScoreVector` 或 STL 容器的内存布局，只定义以下五类记录：

| 记录 | 权威内容 | 非权威/可丢弃内容 |
|---|---|---|
| `ReplayBundleV1` | scenario 引用、session 边界、有序 command/action payload、timeout、expected outcome 条件 | 人类可读 `.sql` |
| `SeedArtifactV1` | seed/provenance id、ReplayBundle 引用、可选 GenerationRecipe、原始观测引用 | IR cache、旧 feature/score/cell |
| `ObservationRecordV1` | SQLSTATE、result status、事务状态、耗时、原始 decision id、确认状态 | 已归一化 reward、plan/feature hash |
| `CampaignCheckpointRecordV1` | §11.6 定义的有限原始计数和 CompatibilityFingerprint | 当前 policy 概率、recent window |
| `ArchiveManifestV1` | 有界 artifact 引用和保存原因 | 旧 archive 排名、cell id |

`SeedArtifactV1` 中可选的 `GenerationRecipeV1` 只包含 generator id、grammar semantics version、根 random seed、稳定 production/action id 序列和必要参数；它不保存 IR node address、容器下标或临时 catalog 指针。recipe 只有在这些语义版本完全匹配时才能生成 IR，否则退回当前 SQL importer 或 replay-only。artifact 之间使用内容 hash/稳定 artifact id 引用，不依赖绝对文件路径；parent id 只表示 provenance，即使父 artifact 已被 compact，子 seed 仍必须能独立 replay。

每个独立 JSON/二进制文件带统一 envelope；同一 JSONL 文件只在首条 header 声明一次 schema/payload type，后续 data record 只保存 sequence、length、payload 和 checksum，避免高速 observation 重复写入大段版本元数据：

```text
format = "sqlbull-artifact"
schema_major / schema_minor
payload_type
writer_version
payload_length
checksum_algorithm / checksum
```

兼容规则只有一套：

- 同一 `schema_major` 只允许新增 optional 字段；reader 忽略未知字段，对缺失 optional 字段使用明确默认值；
- 改变字段语义、单位或必填条件必须增加 `schema_major` 并提供显式 migration；不得用“根据字段内容猜版本”的方式兼容；
- 稳定 id 使用带 namespace 的字符串，枚举以名称写盘，不保存 ordinal、`typeid`、指针、`sizeof`、unordered container 顺序或本地路径；
- JSON 中 `uint64`、时间戳计数和 seed id 使用十进制字符串，避免经过其他语言工具时丢失精度；
- hash 必须同时保存 algorithm/version 和输入规范化版本。版本不匹配时重算；无法重算时该 hash 不参与去重、奖励或兼容判断；
- loader 在分配内存前检查文件大小、record 数、字符串长度、statement 数和嵌套深度上限；单条未知/损坏 optional record 可跳过，必需 replay record 损坏则整个 seed 降级，不能部分执行；
- `ReplayBundle` 是长期兼容边界：后续版本必须保留旧 record reader 或 migration fixture；`SeedArtifact` 至少保留其 replay 能力；`CampaignCheckpoint` 只承诺当前和明确列入 reader 的旧 schema，超出范围直接丢弃统计，不影响 seed replay；
- PostgreSQL/tool 版本变化只代表“文件可读”，不代表“语义可复用”。读取成功后仍必须执行下面的 CompatibilityFingerprint 判定。

兼容判定分两步，不能把 schema 可读性和 DBMS 语义兼容混成一个布尔值：

```text
FormatReadability: CURRENT / MIGRATED / UNREADABLE
SemanticReuseMode: EXACT_RESUME / REPLAY_AND_REEVALUATE / REPLAY_ONLY
```

`EXACT_RESUME` 才允许加载统计 prior 和兼容 recipe；`REPLAY_AND_REEVALUATE` 只重放并用当前 extractor/oracle 重建 feature、score、cell、plan/coverage；`REPLAY_ONLY` 不加载 policy、IR 或旧期望结果，只把完整序列作为待验证 corpus。若存在当前版本不认识的必需 ConnectorAction，则连自动重放也禁止，保留 artifact 并报告 `UNSUPPORTED_ACTION`。

`CompatibilityFingerprintRecord` 保存显式字段，而不是只保存一个不可解释 hash：

```text
dialect_id / dbms_major / server_version_num / dbms_build_id
protocol_schema / connector_action_set
grammar_semantics_version / generator_profile_set_version / ir_abi_version
anchor_id / anchor_hard_semantics_hash
scenario_schema_version / scenario_content_hash
capability_hash / canonical_session_settings_hash
instrumentation_hash
extractor_version / normalizer_version / score_schema_version / plan_hash_version
```

可额外保存上述字段 canonical encoding 的 fingerprint hash 用于快速比较，但最终模式必须逐字段决定并输出差异列表：

- 以上所有影响生成、anchor、scenario、capability 和 policy 统计解释的字段完全相同，才是 `EXACT_RESUME`；
- replay record/action 可读且当前环境能够安全建立 scenario，但 build、instrumentation、extractor、score、plan 或其他语义字段有差异时，是 `REPLAY_AND_REEVALUATE`，旧派生值和 prior 全部清零；
- dialect 不同、必需 action 不可读、scenario 无法安全建立或当前 capability 无法验证时，是 `REPLAY_ONLY`；它只允许人工查看或经当前 importer 重新接纳，不能部分执行旧序列。

PostgreSQL major 变化默认不得进入 `EXACT_RESUME`。即使 SQL 文本仍可执行，也至少执行 `REPLAY_AND_REEVALUATE`，重新编译 anchor 和 expected outcome；无法证明 scenario/action 安全兼容时进一步降级为 `REPLAY_ONLY`。

### 13.2 目录与写入所有权

建议把长期 campaign 与单次 run 分开：

```text
outputs_N/
  queue/
  crashes/
  learning/
    campaigns/<campaign_id>/
      campaign_manifest.json
      checkpoints/
        current.json
        previous.json
      archive/
        index.json
        seed_xxxxxx/
          setup.jsonl
          setup.sql
          sequence.jsonl
          sequence.sql
          meta.json
          recipe.json
          ir_cache.bin
    runs/<run_id>/<core_id>/
      run_meta.json
      observations/events.jsonl
      deltas/campaign_delta.jsonl
```

`campaign_id` 是用户显式 id，或由 dialect、anchor id 和 scenario id 等逻辑范围生成的稳定 id；它故意不包含 DBMS build、grammar hash 等精确指纹，以便新版本能够发现旧 artifact 并决定重新评价。精确 CompatibilityFingerprint 只保存在 manifest/checkpoint 内，目录命中绝不等于可恢复。每次进程启动创建新的 run id；多个 core 只写自己的 run/core 目录，由单独 reducer 周期性合并为 campaign checkpoint，避免共享可变 policy 文件和 archive 锁。

`archive/index.json` 是 `ArchiveManifestV1`，每个 seed 目录的 `meta.json` 是 `SeedArtifactV1`；文件名只是布局，不新增第六种持久化模型。

`meta.json` 至少保存：

    seed id / parent id
    anchor id and version
    dialect, server_version_num, logical major and DBMS build id
    libpq version and protocol version
    grammar/config version
    schema scenario fingerprint
    isolation profile
    canonical session settings fingerprint
    search_path / plan_cache_mode / prepared execution ordinal
    backend/session boundary markers
    random seed
    versioned DecisionTrace record（稳定 action/profile/rule id）
    raw observation reference
    cached feature/score/cell and their algorithm versions
    coverage/plan hash, algorithm version and confidence
    SQLSTATE/error signatures
    RehydrationKind and recipe/IR version

`setup.jsonl` / `sequence.jsonl` 共同构成 `ReplayBundleV1` 的 authoritative replay 输入：每条 record 保存 ordinal、稳定 kind id（SQL command 或后续 ConnectorAction）、完整 payload、timeout、expected outcome 条件和 session boundary。`setup.sql` / `sequence.sql` 只供人阅读，不能由 replayer 再按分号切回 command。缓存的 normalized feature、ScoreVector、archive cell、coverage 和 plan hash 在版本匹配时可用于快速索引，但永远不能替代当前版本重算或确认。

### 13.3 重放与恢复

重放步骤：

    validate ReplayBundle envelope and limits
    -> compare DBMS/config fingerprint and choose SemanticReuseMode
    -> create isolated clean DB/session under current scenario contract
    -> read setup.jsonl records
    -> read sequence.jsonl records in ordinal order
    -> EXACT_RESUME: compare stored expected outcome
    -> REPLAY_AND_REEVALUATE: evaluate with current compiled oracle

跨轮恢复步骤：

    validate envelope/size/checksum and determine FormatReadability
    -> migrate supported record schema; failure affects only that record class
    -> load current statistics checkpoint; failure: fallback previous checkpoint
    -> independently load bounded ArchiveManifest
    -> compare CompatibilityFingerprint field by field
    -> EXACT_RESUME only: replay complete campaign_delta after checkpoint_sequence
    -> EXACT_RESUME only: apply decay and prior caps
    -> load representative ReplayBundle references under all readable modes
    -> EXACT_RESUME/REPLAY_AND_REEVALUATE: replay with current oracle before archive admission
    -> REPLAY_ONLY: retain as corpus; do not auto-execute until current importer/readiness gate accepts it
    -> rehydrate eligible HotSeed lazily only when recipe/IR compatibility permits
    -> reset all RunState-only windows/caches
    -> start with ExplorationGuard enabled

### 13.4 写盘与资源合同

持久化要求：

- 生成线程不为每条普通 SQL 同步写盘；每个 epoch 只提交紧凑计数 delta 和需要持久化的 seed reference；
- 后台单写线程使用有界队列，fault/terminal/frontier/checkpoint 的优先级高于普通 observation；
- checkpoint 按候选数量、墙钟时间、clean shutdown 和内存软高水位触发，不能指望 OOM/kill 时临时保存；
- checkpoint 先写临时文件，flush/fsync 后原子 rename，并保留 current/previous 两代；
- 每个 record/file 使用 §13.1 envelope；checksum 覆盖实际 payload bytes；
- events/campaign_delta 使用 sequence number、checksum 和 append-only record，恢复时忽略最后一条不完整记录；
- checkpoint 读取失败时回退上一个版本，不能用半写文件初始化 policy；
- writer backlog 或写盘延迟超过预算时，先丢弃普通 observation 明细，再暂停 campaign delta；主生成继续使用当前只读选择表和随机 floor；
- checkpoint/archive 超过大小预算时后台 compact，只保留聚合统计和有界代表 seed，不把全量历史重新读入内存；
- 磁盘达到高水位时停止保存普通 ColdSeed，优先保留 confirmed fault 和每个 cell 的代表 seed；
- 磁盘不可写时进入 SAFE_FALLBACK；若连 crash reproducer 也无法可靠保存，则停止运行并明确报警。

允许的崩溃数据损失上限是“最近一个未落盘 epoch”，而不是整个 run。memory soft/hard high-water 必须在 OOM 前主动降低 HotSeed 数量、清空低价值 observation backlog 并请求 checkpoint；如果进程仍被强杀，下轮从最后稳定 checkpoint 和完整 delta 尾部恢复。

### 13.5 Replay 结果

replay 结果分为：

    REPRODUCIBLE
    FLAKY
    NOT_REPRODUCIBLE
    ENVIRONMENT_MISMATCH
    REPLAY_INFRA_FAILURE

只有 REPRODUCIBLE fault 才进入 confirmed fault 统计。FLAKY 保留诊断，但不给 learner 极高奖励；环境不匹配和 replay 基础设施失败不评价生成策略。

## 15. 分阶段实施计划

每个阶段都必须满足：

- 独立 feature flag；
- 能退回上一阶段模式；
- 新格式遵循 §13.1 envelope、稳定 id 和迁移合同；
- 对 legacy 吞吐、合法率和重放率有对照；
- 未达到验收条件时不进入下一阶段；
- 任何新模块异常都不能伪装成 query reward。

### 阶段 0：基线稳定和构建链

实现：

- 确认 source of truth；
- 修复 TYPESTRING/null dereference；
- 修复 queue 除零、tie 和裸 lineage；
- 修复 plan 新颖性判断；
- 移除 PostgreSQL 简单分号切分；
- 用 `PQsendQueryParams` 建立 single-command boundary，正确实现 row mode 和 drain-to-null；
- 获取 SQLSTATE、非本地化 severity、诊断字段和 `PQtransactionStatus`；
- 替换非法 database reset，建立 `ROLLBACK/DISCARD ALL/schema rebuild/fingerprint`；
- 把硬编码预算配置化；
- 建立 deterministic replay；
- 定义并生成最小 `ReplayBundleV1`，不再把 C++ 对象或分号拼接 SQL 当作 replay 格式；
- 增加 supervisor、有界 restart/reconnect 和 FailureDomain；
- 以 `PostgreSQL/docker/rsg_cpp` 为本方案 source of truth。

验收：

- legacy fuzzing 行为可开关保持；
- PostgreSQL Docker 可稳定构建；
- 字符串语句不会进入 IR-only 路径；
- 函数体、dollar-quoted text、quoted identifier 和字符串中的分号不会被拆分；一个 QueryStmt 不能偷偷执行两个 top-level command；
- error/cancel 后 result 能 drain 到 null，下一 command 不出现 protocol busy/残留 result；
- `PQTRANS_INERROR`、`PQTRANS_UNKNOWN` 和 reconnect 后 session-local 状态不会被误判为可继续；
- 相同 seed/scenario/canonical settings 可以重放；
- DBMS 永久不可用时能在总时限内停止，而不是无限等待；
- 任意阶段关闭新 feature 后 legacy 模式仍能运行。

- PostgreSQL backend 在 PREPARE 后退出；
- server 在 reconnect 期间持续不可用；
- query timeout、client watchdog timeout 和连接丢失；
- 事务进入 aborted 状态；
- `PQsetSingleRowMode` 调用时序错误；
- fatal result 后故意残留未 drain result；
- `DISCARD ALL` 被错误放入事务块；
- plan observer 意外增加 live prepared execution count；
- server major/canonical `search_path`/`plan_cache_mode` 与 replay metadata 不一致；
- CatalogState 人为漏 apply 一个 DDL delta；
- plan observer 返回错误、超时或不稳定 plan；
- coverage 第一次出现、重放消失；
- result 返回超大行数和错误文本；
- archive 达到 cell、内存和磁盘上限；
- checkpoint 截断或 checksum 错误；
- events.jsonl 最后一条半写；
- campaign_delta 最后一条半写、sequence number 跳跃或重复；
- OOM/kill 发生在 epoch、seed 写入和 checkpoint rename 的不同阶段；
- background writer 变慢、队列满和 archive compaction 超时；
- 历史 prior 被人为设置成单 profile 极高 reward/attempts；
- soft heuristic 错误拒绝大量候选或规则版本缺失；
- 正向 anchor invariant 被错误接入全局 exploration filter；
- ExplorationArchive 全是远离当前 anchor 的随机 seed；
- restored seed 的 IR/recipe checksum 或版本不兼容；
- EXACT_RESUME、REPLAY_AND_REEVALUATE 和 REPLAY_ONLY 指纹组合；
- anchor UNSAT、UNSUPPORTED 和 relaxation；
- grammar/build/scenario version 在恢复时变化；
- 两个 core 同时产生相同 seed id。

每项测试验证五件事：

1. 是否被正确分类；
2. 是否在有界时间内结束或恢复；
3. 是否错误更新 learner；
4. 是否能保留足够的诊断和 reproducer。
5. legacy/uniform/reservoir 随机 floor 是否仍满足合同。

## 18. 锚点示例

### 18.1 复杂窗口查询

```text
invariants:
  result_is_success
  connection_alive

terminal_goals:
  HAS_SELECT
  HAS_WINDOW
  HAS_GROUP_BY

preferences:
  HAS_JOIN weight 1
  HAS_CTE weight 1
  subquery_depth >= 1 weight 2
  observed plan_node(WindowAgg) weight 3

forbid:
  timeout

validity:
  require_execute_success = true
```

演化可能是：

    single table aggregate
    -> aggregate + window
    -> join + aggregate + window
    -> CTE + join + aggregate + window
    -> 增加相关子查询或多类型表达式

每一步必须通过 invariants；尚未满足全部 terminal_goals 但取得进展时进入 FrontierArchive，完整满足后才进入 CompletedArchive。

### 18.2 Prepared statement 生命周期

```text
invariants:
  connection_alive
  related object
  same backend session

terminal_goals:
  SQL_PREPARE
  INVALIDATION_TRIGGER
  SQL_EXECUTE_PREPARED
  ordered retain -> invalidate -> reuse

preferences:
  observed PLAN_CACHE
  semantic CACHE_INVALIDATION
  observed CACHE_INVALIDATION if instrumentation available
  changed generic_plans/custom_plans count
  new coverage

dimensions:
  plan_cache_mode in [auto, force_custom_plan, force_generic_plan]
  execution_ordinal in [1, 5, 6+]
  invalidation_kind in [definitional_ddl, statistics, search_path]

reuse_outcome:
  success_allowed = true
  allowed_exact_sqlstates = scenario- and stage-specific set
  postconditions = [prepared_statement_still_registered, connection_alive]
```

演化不是随意组合 PREPARE、ALTER 和 EXECUTE，而是根据依赖图保证 invalidation trigger 与 prepared statement 引用的 relation/function/index 相关，并控制 `plan_cache_mode` 与执行序号。PostgreSQL 17 在 definitional DDL、statistics 或 `search_path` 变化后会按规则重分析/重规划；“成功重规划”和“明确的不兼容错误”应是两个独立 scenario/oracle，不能把任意 ERROR 当成缓存命中证据。

### 18.3 Cursor 跨事务生命周期

成功跨 commit 的锚点必须显式使用 held cursor：

```text
invariants:
  same backend session
  transaction_state follows automaton

terminal_goals:
  BEGIN
  DECLARE CURSOR WITH HOLD
  COMMIT
  FETCH same_cursor

forbid:
  FOR UPDATE with WITH HOLD
  FOR SHARE with WITH HOLD

fetch_outcome:
  success_allowed = true
  postconditions = [cursor_still_registered, transaction_idle]
```

负向锚点另行定义为 `WITHOUT HOLD -> COMMIT -> FETCH`，其 FETCH 阶段只允许 exact SQLSTATE `34000`。两者使用不同 anchor id/namespace，避免 learner 通过生成默认 `WITHOUT HOLD` 错误来“完成”成功路径。

### 18.4 只给 SubsystemTag 的锚点

如果用户只指定 `EXECUTOR_WINDOW`：

1. AnchorCompiler 将其转换为代理目标 HAS_WINDOW；
2. generator 优先生成合法 WINDOW_QUERY；
3. plan 中出现 WindowAgg 后，将 evidence 从 INFERRED 提升为 OBSERVED；
4. observed plan/coverage 才提供较高奖励；
5. 没有 observed evidence 时，系统明确报告“接近代理目标”，而不是宣称已经命中内部模块。

## 19. 健壮性场景矩阵

| 场景 | 检测依据 | 运行时处理 | 是否更新 learner |
|---|---|---|---|
| anchor 语法错误或谓词冲突 | AnchorCompiler diagnostics | 拒绝 GUIDED，保留 LEGACY/OBSERVE | 否 |
| dialect capability 不支持 | capability mask | 拒绝、显式 relaxation 或代理目标降级 | 否 |
| anchor 暂时未完成 | automaton stage 有进展 | 进入有界 FrontierArchive | 是，使用阶段进度 |
| anchor 长期不可达 | frontier TTL、无正进度窗口 | 降低预算/换 profile，最终报告 STALLED | 仅更新已执行 profile |
| baseline 样本不足 | 分层样本计数 | 使用保守先验，继续 warm-up | 不做淘汰性更新 |
| generator/repair 耗尽 | attempt/pass budget | circuit breaker，fallback lane | 只记生成器可用性，不算 SQL invalid |
| soft rule 试图拒绝候选 | rule strength contract | 视为 rule-engine fault，降级该规则/关闭 guided reject | 否 |
| UNKNOWN 候选比例骤升 | tri-state counters | 有界送入 exploration/Quarantine，检查模型覆盖 | 不做负向更新 |
| 单 profile 选择垄断 | actual share、probability cap | ExplorationGuard 截断并重归一化 | 是，但冻结异常 policy 发布 |
| 选择熵/随机 floor 越线 | epoch metrics | 回滚稳定 mixture 或 SAFE_FALLBACK | 暂停更新 |
| 历史 prior 与当前证据冲突 | recent vs prior、override deadline | 衰减/截断 prior；超限则本轮忽略 CampaignState | 只更新 run-local |
| Campaign 指纹不完全匹配 | CompatibilityFingerprint | REPLAY_AND_REEVALUATE 或 REPLAY_ONLY | 默认不复用 prior |
| SQL 语法/语义失败 | SQLSTATE + FailureDomain QUERY | rollback model delta，更新合法率 | 是 |
| PostgreSQL major/capability 变化 | `PQserverVersion`、capability fingerprint | 重编译 anchor，隔离旧 archive/plan hash | 否 |
| CatalogState 不确定 | 未建模 DDL、cascade、结果矛盾 | 标记 DIRTY，停止 sequence，reset | 否，记 model divergence |
| 事务 aborted | PQtransactionStatus、25P02 | rollback/savepoint 恢复；失败则停止 sequence | 只评价触发它的 query |
| active command/result 未 drain | PQTRANS_ACTIVE、busy/protocol state | 继续有界 drain；失败则丢弃连接 | 否，记 connector fault |
| `DISCARD ALL` 位于事务块 | transaction status + SQLSTATE | 先 ROLLBACK 到 IDLE，再重试一次；仍失败则 recovery | 否 |
| PREPARE 后发生 DDL/stats/search_path 变化 | object/GUC dependency + stage | 按 scenario oracle 验证重分析/重规划，不假定旧计划 | 是 |
| live plan observer 改写 prepare 次数 | `generic_plans/custom_plans` 前后差异 | 丢弃 observer 信号，改用 diagnostic replay | 否 |
| `WITHOUT HOLD` cursor 跨 COMMIT | cursor registry + `34000` | 只在负向 cursor anchor 的 FETCH stage 接受 | 依 anchor |
| `WITH HOLD` cursor 跨 COMMIT | cursor registry + success | 同 session 继续；reconnect 后不可恢复 | 是 |
| temporary table 在另一连接不可见 | session-bound metadata | plan 标记 SAME_SESSION_REQUIRED，不当 undefined-table 生成失败 | 否 observer reward |
| expected error 出现在错误阶段 | event/stage + SQLSTATE 不匹配 | 当普通 query failure 处理 | 是 |
| statement timeout | SQLSTATE、statement_timeout | cancel/drain，按事务状态恢复 | 是，有限惩罚 |
| client watchdog timeout | 无响应且 DBMS 状态未知 | session lost，停止 sequence，RECOVERING | 确认前否 |
| backend crash/连接丢失 | backend/connection 状态 | 保存候选 fault，重启后完整 replay | 确认后有限更新 |
| DBMS server 长期不可用 | health check + recovery deadline | SAFE_FALLBACK，超过总上限停止 | 否 |
| scenario setup/fingerprint 失败 | setup result、catalog probe | 重试有界；禁用 scenario；降级 basic | 否 |
| isolation profile 前置条件失效 | volatility/event/session postcondition | 升级 FULL_SCHEMA_RESET，隔离快路径结果 | 否，记 classifier fault |
| result 过大 | row/result byte budget | 截断内容但完整 drain，继续运行 | 是，增加成本 |
| FeatureExtractor 失败 | extractor status | 保留执行结果，进入 Quarantine | 否 |
| plan observer 失败 | observer status | 丢弃 plan 信号，不影响主 query | 否 |
| plan 依赖 session-local 状态 | PlanEligibility | live observer 跳过；需要时完整 diagnostic replay | 是，但主执行无 plan reward |
| plan shape 不稳定 | 重放 shape 不一致 | 降低 confidence，不进入强 novelty | 低置信度更新 |
| coverage 首次出现但不可复现 | confirmation replay | 保留 AFL seed，降低 learner 信号 | 不给 confirmed reward |
| crash/assert 不可复现 | fault replay | 标记 FLAKY，保留诊断 | 不给高 reward |
| archive 内存满 | memory high-water | HotSeed 降为 ColdSeed、淘汰低优先级 | 是 |
| ExplorationArchive 充满低相关 seed | reservoir quota/TTL | 正常 reservoir 替换，不扩容、不降低随机 floor | 只记当前执行反馈 |
| restored seed 无法 rehydrate | recipe/IR/importer version | 降级 `SEED_REPLAY_ONLY`，继续加载其他 seed | 否 |
| epoch observation buffer 满 | queue high-water | 聚合同类计数、丢普通明细，使用旧选择表 | 不更新丢失明细 |
| background writer/backlog 超限 | queue/latency budget | 暂停 campaign delta，保留 run-local/random | 否跨轮更新 |
| OOM/kill 突然退出 | supervisor + checkpoint sequence | 下轮回退稳定 checkpoint/delta，RunState 全清 | 否额外惩罚 |
| archive 磁盘满 | disk high-water/write error | 停存普通 seed，优先 fault；必要时停止 | 否 |
| checkpoint 损坏 | schema/checksum | 回退上一个稳定 checkpoint | 否 |
| replay 环境版本不同 | build/grammar/scenario hash | 标记 ENVIRONMENT_MISMATCH | 否 |
| 多核重复或状态竞争 | core namespace、seed hash | 每 core 独立写入，离线去重合并 | 各 core 独立 |
| 用户运行中切换 anchor | anchor version 改变 | 新 namespace，旧 seed 只读 | 新策略重新 warm-up |

### 19.1 故障归因优先于奖励

同一表面现象可能来自不同原因。例如“连接断开”可能是 backend crash、server restart、client watchdog 主动断开或 Docker 基础设施故障。确认前不把它当作高价值 fault。

归因顺序：

    observer 自身是否失败
    -> infrastructure 是否健康
    -> session 是否丢失
    -> query SQLSTATE/结果
    -> replay 是否确认

只有 FailureDomain=QUERY 的正常错误影响合法率；只有 CONFIRMED_DBMS_FAULT 进入正式 fault 指标。

### 19.2 恢复预算

恢复过程必须有三级预算：

    单次连接等待
    单个 seed 的 restart/replay 次数
    整个 fuzzing run 的连续基础设施失败窗口

超过第一级重试；超过第二级放弃当前 seed；超过第三级进入 SAFE_FALLBACK 或停止。所有阈值配置化并写入运行元数据。

### 19.3 模型漂移处理

CatalogState、SessionState 和 DBMS 实际状态出现矛盾时，不尝试在任意状态上继续“学习修复”。首期选择保守策略：

1. 标记当前 seed MODEL_DIVERGENCE；
2. 保存最后一个确定状态和触发语句；
3. reset DB/session；
4. 从 setup + prefix replay 验证；
5. 可重现则修复 state transition；不可重现则进入诊断队列。

### 19.4 多核和长期运行

首期每个 AFL core 使用独立：

    archive namespace
    RunState / read-only selection table
    observation and campaign-delta log
    seed id prefix

不共享可变 learner 内存，也不让多个 core 直接改写 CampaignState。单独 reducer 只读取各 core 已完成的 epoch delta，按可交换计数和 canonical seed hash 合并，原子发布下一版只读 campaign checkpoint；运行中的 core 可以只在 restart 或安全 epoch 边界加载，不能被中途强制替换 policy。跨 core 导入 seed 时必须重新 replay，并根据本 core 的 build/scenario/anchor 重新评分。

长期运行还要定期：

- 轮转 observation log；
- 校验 archive checksum；
- 清理过期 Quarantine 和 Frontier seed；
- 保留稳定 run-local selection snapshot，并按 §13 保存独立 campaign checkpoint；
- 衰减并封顶跨轮 prior，删除过期 campaign delta；
- compact ExplorationArchive/guided representatives，不加载全量历史；
- 记录 memory/disk high-water；
- 对代表 seed 做抽样 replay，监测环境漂移。

## 20. 上线与 Go/No-Go 准则

### 20.1 LEGACY 基线

必须先得到稳定的合法率、吞吐、coverage 和 replay 指标。如果 baseline 本身不稳定，不能据此评价 guided 方案。

### 20.2 OBSERVE

Go 条件：

- 不改变 seed 选择和 RSG 决策；
- coverage/AFL 保存行为与 legacy 可解释地一致；
- infrastructure failure 能被排除；
- PostgreSQL connector contract 全部通过：single command、row mode 时序、drain-to-null、SQLSTATE、transaction status、timeout/cancel 和 clean reset；
- canonical settings 与 `server_version_num` 完整写入 observation/replay metadata；
- 资源开销不越过配置保护线。

否则回到 LEGACY 修复观测链。

### 20.3 GUIDED_SHADOW

Go 条件：

- profile 选择分布没有单一 profile 异常垄断；
- 按 hypothetical selection 验证 legacy/uniform/reservoir floor、profile cap 和 entropy；
- reward 可以从 observation log 离线重算；
- anchor progress 与人工检查样例一致；
- UNSAT/UNSUPPORTED anchor 不会启动学习；
- PREPARE/cursor/temp/search_path 锚点的 session/transaction oracle 与 PostgreSQL 17 集成测试一致；
- run-local policy snapshot 可回滚。
- soft/UNKNOWN rule 即使判断错误也不会改变 legacy 实际执行或形成 hard rejection。

否则继续 shadow，不影响真实生成。

### 20.4 GUIDED Canary

只给少量执行预算或单个 core 启用。Go 条件：

- 合法率不低于保护线；
- 固定墙钟时间的有效 SQL 吞吐没有不可接受下降；
- anchor proximity 有正向趋势；
- archive 多样性没有坍缩；
- 实际随机探索比例、最大 profile share、选择熵和重复模板率均在保护线内；
- epoch learner、writer 和 archive admission 开销不越过热路径预算；
- replay 和 fault confirmation 正常；
- 没有新增未界定的 crash/hang 来自 fuzzer 自身。

任一核心指标连续多个窗口越线，自动回滚稳定 run-local selection snapshot 并进入 SAFE_FALLBACK。

### 20.5 Campaign Warm Start

只有 run-local GUIDED Canary 稳定后启用。本阶段不重新定义兼容或恢复逻辑，直接以 §11.6、§13 和 §16.3 为合同。Go 只看三个结果：archive-only 相对冷启动有收益；小权重 prior 相对 archive-only 还有独立的 stage/terminal 收益；错误 prior、旧版本 artifact、restart/OOM 和 writer failure 均不会越过随机性、吞吐、内存或数据一致性保护线。任一项不满足即保持 `campaign.enabled=false`，继续使用纯轮内学习。

### 20.6 全量运行

全量启用仍保留固定比例 legacy、uniform profile 和 ExplorationArchive exploration，持续作为在线对照和逃离局部最优的通道。不得删除 legacy feature flag、ExplorationGuard、replay 工具和独立 FaultArchive。

## 21. 总结

最终实现和完成边界以 §1.1 为唯一依据，总体数据流以 §5 为唯一依据，不在本节重复定义。

定稿后的核心取舍是：PostgreSQL 17 执行/replay、三路生成、有界 archive 和轮内有限 profile 学习属于主产品；archive-only 跨轮恢复必须可用，统计 prior 只有证明额外收益才启用。运行时 IR、feature、score 和所有权结构不写盘；长期价值由版本化 ReplayBundle 保证，旧派生状态不兼容时重算，旧统计不兼容时丢弃。

系统即使关闭全部经验层，也必须继续稳定地产生、执行和保存随机 SQL。经验层的唯一职责是在不破坏合法率、随机下限、多样性、吞吐和资源上限的前提下，提高长期锚点命中概率。
